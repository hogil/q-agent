## 1. GPU — H100 x 20

### 수요등록 최종 (시스템 실측 산출)
| # | 등록 항목 | 학습항목 | 입력 | 산출 |
|---|---|---|---|---|
| 1 | GLM-5.2 판단·도메인·코딩 SFT | TOKEN/Text LLM | 743B, MoE체크, 1.5B tok, ep3, 30일/dev2 | TOKEN 4.89 |
| 2 | Qwen3.5-397B 멀티모달 SFT | TOKEN/Multimodal | 397B, MoE체크, 1.2B tok, ep3, 30일/dev2 | TOKEN 2.09 |
| 3 | Qwen3-Embedding-8B+Reranker-8B | TOKEN/Text LLM | 16B, 500M tok, ep5, 15일/dev2 | TOKEN 0.23 |
| 4 | GLM-5.2 Agent 정책학습 | STEP/GRPO eq=13 | 743B(단위 B!), step 70K, 15일/dev2 | STEP 2.63 |
| 5 | Qwen3-VL-Embedding 튜닝 | TOKEN/Multimodal | 8B, 300M tok, ep15, 15일/dev2 | TOKEN 0.21 |

**합계 B300 10.05 → H100 20.1장** (스펙 계수 B300:H100:A100 = 1:2:4)

시스템 공식(해독·검증됨): TOKEN = 모델크기×토큰×epoch×K(MoE3/dense6) / STEP = 모델크기×step×eq×4000 / B300 = 연산량(E)÷(137×dev일수)
함정: 모델크기 단위 M/B 오입력(1,000배), dense에 MoE 체크(절반), dev 주기 짧을수록 장수 증가

**2026-08-06 역검증**: 공식을 코드로 재실행한 결과 연산량 5건 전부 정확히 재현, B300은 4건 일치. [1]만 계산 4.88 vs 문서 4.89로 0.01 차이(화면 반올림). **어느 쪽이든 H100 환산 20.1장으로 동일 — 신청 근거 영향 없음.** 상세는 `설계/GPU신청_종합정리.md` §3.

### 운용 배분
- 서빙: 판단 LLM GLM-5.2 FP8 12장(TP) + 고정밀 VLM Qwen3.5-397B 5장 + 경량 VLM·검색기 2장 + 회귀평가 1장
- 학습 모드: 16장 SFT/DPO 전환(월 4회), 경량 서빙 4장 유지 — 이미지 기능 무중단
- vLLM: continuous batching + PagedAttention + prefix caching

**★ 제출본 문구 정정 필요**: 서술형 '적합성' 필드의 `적재 8장` 은 H200(141GB) 기준 초안이 남은 것이다. H100은 카드당 80GB이므로 743 ÷ 80 = 9.3 → **적재 최소 10장**이어야 한다. 8장(640GB)으로는 가중치가 물리적으로 안 올라간다. 서빙 12장·총 20장 결론은 불변.

## 2. VM — BIG VM x 5 (Ubuntu 24.04 LTS)

### 웹 입력값 (확정)
서버 5 / vCPU 합계 320 / MEM 합계 5,120GB / DISK 합계 153,600GB / 백업 153,600GB·5대 / NAS 102,400GB / OBJ 51,200GB

### 상세 (각 64core / 1,024GB / 30,720GB, NAT 전부 X)
| Host | LB | 탑재 서비스 | 대당 근거 요약 |
|---|---|---|---|
| qagent-svc01 | O | Agent Runtime + Chat GW + 인메모리 캐시 | CPU 40(세션28+캐시8+GW4)→64 / MEM ~800GB(시계열207+특징300+사례200+세션) |
| qagent-svc02 | O | Agent HA + Prometheus·Grafana·Loki + 회귀평가 | CPU 60(28+16+16)→64 / MEM ~716GB(TSDB+평가+캐시복제400) |
| qagent-data01 | X | PostgreSQL16+pgvector(primary) + ETL | CPU 61(200QPS 50+ETL 11)→64 / MEM ~1,020GB(HNSW300+핫캐시400+버퍼256) |
| qagent-data02 | X | PG standby + 백업(pgBackRest) + 감사로그 | 승격 시 primary 동일 부하·956GB 동일 상주 |
| qagent-train01 | X | 데이터셋 빌드 + 웨이트 병합(시분할) | CPU 63(5.0e6core·s÷22h)→64 / MEM 병합900GB·빌드820GB |

HA: API=svc01/02, DB=data01/02 교차. 학습 병합을 train01 전담 → GPU 슬롯 회당 3~5h 절약(월 4회)

## 3. 스토리지

- **NAS 102,400GB (100TB)**: 가중치 세대 (743+1,486+497)GB×3세대=8.2TB + 체크포인트 500GB×월4×3개월=6TB + 데이터셋 1.5TB×4세대=6TB + 캐시 3TB + 확산 증가·프리컴퓨트 — GPU 노드+train01 공유 마운트
- **OBJ 51,200GB (50TB)**: 이미지 2만 장/일×2MB + Map 5만 장/일×0.5MB → 65GB/일 × 600일 = 39TB + 스냅샷·아카이브 10TB
- 백업: VM DISK ×1배(일 단위) + WAL 아카이브 → NAS

## 4. DB — 직접 설치 (관리형 반려 후 확정)

- 관리형 신청분(dbqie, 등급 C 32c/128GB/4TB, 월 748,153원) **반려** → data01/02 PostgreSQL 16 + pgvector 직접 설치 (원래 설계로 회귀, VM 산정근거와 정합)
- 이점: 64c/1TB로 스펙 상향(인덱스 전량 상주 가능), pgvector 버전 자유(0.7+ halfvec), 월 비용 절감
- 데이터 용량 설계(유지): 원문 200 + 벡터 색인 300 + 키워드 색인 200 + 판정 이력 274(3년) + 체크포인트 450(90일) + 시계열 요약 500 = 1,900GB + 여유 ≈ 4TB (로컬 30TB 內)
- 직접 운영 몫: 스트리밍 복제·승격 절차 / pgBackRest 백업·복구 리허설 분기 1회 / 패치는 학습 주기 창에서만 / postgres_exporter / 사내 DB 보안 정책

**2026-08-06 실측**: 테스트 VM에 **PostgreSQL 16.14 + pgvector 0.8.1** 설치 완료, 스키마·가드·평가까지 동작 확인. 0.7 이상이므로 **halfvec 사용 확정** — 벡터 색인 크기가 절반이 되어 위 300GB 산정은 여유가 생기는 방향. 구축 절차는 `설계/DB_구축_실행순서.md`.

## 5. 비용·ROI

- 투자금액: **347,794,165원/년** (BIG VM 5대 + NAS 100TB + OBJ 50TB, 사내 과금)
- 기대효과: [(4h/8h)-(2h/8h)] × 연봉 80,000,000원 × 1,000명 = **연 200억 원** (판정 업무 일 4h→2h)
- **ROI 약 57.5배, 투자 회수 약 6.4일**
- 검증: 가동 후 골든 시나리오 정답률·건당 처리 시간 실측, 분기 보고. GPU 가동률·처리 건수 월간 리포팅

---

## 6. 네트워크·정책

- AZ: H100 클러스터와 **동일 AZ 필수** (도구 호출 건당 5~15회 왕복)
- 망: 제조·사내망. 기간계는 **정보계(DW·ODS) 경유** — 운영계 직접 조회 금지, statement_timeout·LIMIT 필수
- LB: svc01/02 Agent API 앞단. EIP 없음. 과금: 정액
- HITL: Agent 접근은 조회 전용, 조치는 엔지니어 승인 후 실행
