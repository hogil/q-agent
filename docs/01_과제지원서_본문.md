**전사/사업부 AI 과제 공모 지원서 — 본문**

## 1. 추진 배경 및 필요성

### 1.1 현행 업무의 문제

불량 하나를 판단하려면 엔지니어가 SPC 트렌드, wafer map, 결함 이미지, Inform Note 조치이력, MES·YMS 기준정보를 서로 다른 기간시스템에서 하나씩 열어 대조해야 한다. 이 과정에서 네 가지 문제가 반복된다.

첫째, **시간**이다. 시스템 사이를 오가며 화면을 열고 수작업으로 대조하는 데 판정 시간의 대부분이 쓰인다. 정작 판단 자체에 쓰는 시간은 그 일부다.

둘째, **편차**다. 같은 현상을 놓고도 엔지니어의 경험에 따라 다른 결론이 나온다. 어떤 데이터를 봤는지, 무엇을 안 봤는지가 사람마다 다르기 때문이다.

셋째, **공백**이다. 야간과 주말에는 대응이 다음 근무까지 밀린다. 그 사이 같은 원인의 불량이 계속 생산된다.

넷째, **휘발**이다. 왜 그렇게 판단했는지가 사람의 머릿속에 남고 시스템에 축적되지 않는다. 담당자가 바뀌면 같은 문제를 처음부터 다시 푼다.

### 1.2 기존 대안으로 해결되지 않는 이유

| 대안 | 왜 부족한가 |
|---|---|
| 사내 LLM API | 판단에 필요한 사내 DB 조회·이미지 판독을 하지 못한다. 검색기 파인튜닝, 선호학습, 에이전트 토큰 구조를 제공하지 않아 우리 데이터로 정확해지는 경로 자체가 없다 |
| 사내 공용 RAG | 사내 용어 병기(ACI → 세정 후 계측), 설비 ID 토큰 보호(PHO-D03을 통짜로), 한국어 형태소 색인, 메타 필터, 임베딩·리랭커 교체, recall 지표 열람이 모두 불가하거나 대부분 불가하다 |
| BI·대시보드 | 사람이 봐야 할 화면을 늘릴 뿐, 판단을 대신하지 않는다. 화면이 늘수록 대조할 것이 늘어난다 |
| 규칙 기반 SPC 알람 | 이상이다까지는 알려주지만, 왜 그런가·무엇을 해야 하나에는 답하지 않는다. 대체 대상이 아니라 이 시스템의 트리거 입력으로 그대로 쓴다 |

### 1.3 지금 시작해야 하는 이유

판정 이력과 Inform Note가 학습 자산으로 쓸 만한 양에 도달했다. 오픈 LLM이 MoE·FP8 형태로 사내 온프렘 서빙이 가능한 수준까지 성숙했다. 그리고 사내 GPU 수요등록 체계를 통해 확보 경로가 열려 수요등록을 완료한 상태다. 세 조건이 동시에 맞는 시점이다.

## 2. 과제 목표

### 2.1 최종 목표

확인 → 판단 → 조치까지 스스로 수행하되, **모든 판단은 조회된 실데이터를 근거로 인용해야 하고, 현장에 영향을 주는 조치는 반드시 사람 승인을 거치는** 품질 관리 시스템을 구축한다.

두 개의 입구를 둔다. 엔지니어가 채팅으로 묻는 Chat 모드와, 이상 이벤트를 시스템이 스스로 질문으로 바꿔 넣는 무인 감시 모드다. 분석하는 코어는 하나로 공유한다.

### 2.2 연차별 목표

| 구분 | 1차년 (구축·검증) | 2차년 (확산·자동화) |
|---|---|---|
| 적용 공정 | 포토 1개 | 포토 + etch + CMP (3개) |
| 운영 형태 | 그림자 운영 → Chat 파일럿 → 무인 접수 | 3개 공정 정상 운영 + 저위험 자동조치 |
| 조치 권한 | 전건 사람 승인 (자동 실행 0건) | 되돌릴 수 있는 조치만 자동, 나머지는 승인 |
| 핵심 산출 | 조사 코어 · 도구 8종 · 검증기 · 골든셋 30건 · 회귀 게이트 | 공정별 조사규칙 템플릿 · 자동조치 화이트리스트 · 확산 표준안 |
| 닫는 조건 | 골든셋 일치율 기준선 확보 + 무인 접수 누락 0건 | 3개 공정 회귀 통과 + 자동 실행 전건 감사 |

### 2.3 정량 목표

| 지표 | 현재 상태 | 1차년 목표 | 2차년 목표 | 측정 방법 |
|---|---|---|---|---|
| 판정 소요 시간 | 1인 일 4시간 | 포토 공정에서 실측 개시 | 1인 일 2시간 | 건당 처리 시간 로그 |
| 골든셋 판정 일치율 | 미측정 | **기준선 실측 후 목표치 확정** | 1차년 기준선 대비 하락 없음 | 골든셋 회귀 러너 |
| 검색 recall@10 | **0.500 실측** (골든 4건 / 색인 50건) | 질의 재작성·리랭커 적용 후 재측정하여 상향 | 공정 확대 후에도 유지 | `eval_recall.py` |
| 야간·주말 커버리지 | 없음 | 무인 접수 2주 연속, 누락 0건 | 3개 공정 24/7 | 접수 로그 대조 |
| 근거 없는 판단 채택 | — | **0건** | **0건** | 검증기 차단 로그 |
| 미승인 L2 조치 실행 | — | **0건** | **0건** | 감사 로그 |
| 자동 실행 조치 | — | **0건 (의도적)** | 화이트리스트 ◇건, 오판율 실측·공개 | 감사 로그 |
| 등록 Inform Note | — | 누적 건수 리포팅 개시 | 선순환 지표로 관리 | 적재 로그 |

> 목표 정답률에 임의의 퍼센트를 적지 않는다. 1차년 그림자 운영에서 기준선을 실측한 뒤 목표치를 확정하고, 그 값을 회귀 게이트로 고정한다. 지금 제시할 수 있는 실측치는 검색 recall@10 = 0.500 하나뿐이며 그대로 적었다.

### 2.4 정성 목표

판단 근거가 시스템에 남아 감사 대응이 가능해진다. 엔지니어의 조사 노하우가 조사규칙 문서와 Inform Note로 자산화되어 사람에 묶이지 않는다. 신규 엔지니어가 선배의 판단 경로를 그대로 따라 볼 수 있어 학습 곡선이 짧아진다.

## 3. 과제 범위

### 3.1 포함

조사 코어(LangGraph 오케스트레이션, ReAct 도구 루프), 도구 8종(SQL 5종·vision 2종·RAG 1종), 판단 그라운딩 검증기 5칙, 조치 등급 체계 L0~L3와 승인 게이트, Chat UI, 이상 이벤트를 질문으로 바꾸는 어댑터, Inform Note 등록 선순환, 골든셋과 회귀 평가 러너, 그리고 2차년의 공정별 조사규칙 템플릿과 확산 표준안을 포함한다.

### 3.2 제외

기간계 원본 시스템은 변경하지 않는다. 조회 전용 계정만 발급받는다. 운영계에 직접 붙지 않고 정보계(DW·ODS)를 경유한다. L3 자동조치의 전면 개방은 이 과제 범위 밖이며, 시나리오별로 정확도를 실측한 뒤 개별 심의로 승격한다. 설비 제어성 조치는 2차년에도 계속 사람 승인 대상이다.

### 3.3 외부 인터페이스

기간계 SPC·MES·YMS·EES·QMS를 정보계 경유 조회 전용으로 연결한다. 알림과 승인은 사내 메신저·메일을 사용한다. 모델 서빙은 사내 GPU 클러스터(H100 20장)에서 수행한다.

## 4. 추진 방안

### 4.1 시스템 구조 — 코어 하나, 입구 둘

```
  ┌─ Chat  : 엔지니어 질문 "GATE ACI CD +0.9 올랐어. 어디 문제고 어떻게 조치?" ─┐
  └─ 무인  : 감지 이벤트 → 질문으로 변환 (Event-to-Question Adapter) ──────────┘
                     │
                     ▼
  ┌──────────────── 조사 코어 (LangGraph) ────────────────────────────────┐
  │  adapter        증상 분류 → 해당 조사규칙 로드                          │
  │  investigator ⇄ tools   ReAct 루프: LLM이 도구를 골라 반복 호출          │
  │  judgment       증거팩(EV-0..N) → 구조화 판단서 → 검증기 5칙            │
  │  action         규칙표로 등급 결정 → L2는 승인 대기(HITL) → 실행         │
  │  answer         검증 통과 판단서만 렌더링 (자유 작문 금지, [EV-n] 인용)   │
  │  register       Inform Note 초안 → 엔지니어 확정 → 검색 자산            │
  └──────┬────────────────────────────────────────────┬──────────────────┘
         │ 도구가 조회                                   │ 등록이 자산이 된다 (선순환)
         ▼                                              ▲
  기간시스템 (조회 전용)                          지식 자산 (현업이 등록)
  SPC·MES·YMS·EES·QMS + vision CNN + RAG        Inform Note·조사규칙·이미지
```

| 단계 | 하는 일 |
|---|---|
| adapter | 증상을 분류해 해당 조사규칙 문서를 시스템 프롬프트로 주입 (조사 순서·함정이 함께 들어간다) |
| investigator | ReAct 루프. LLM이 도구를 골라 반복 호출하고, 결과가 대화에 쌓이며 사실이 모인다. 더 부를 도구가 없으면 조사 종료 |
| judgment | 증거팩을 받아 구조화 판단서 생성 → 검증기 5칙 통과분만 채택. 실패 시 오류를 붙여 재생성, 증거 부족이면 조사로 회귀 |
| action | 규칙표로 조치 등급 결정. L2 이상은 그래프를 멈추고 사람 승인을 기다린다 (승인이 몇 시간 뒤 와도 그 지점부터 재개) |
| answer | 검증 통과 판단서만 렌더링. 자유 작문 금지, 모든 문장에 [EV-n] 근거 인용 |
| register | Inform Note 초안 생성 → 엔지니어 확정 → 검색 자산으로 적재 (다음 사건이 이걸 쓴다) |

### 4.2 핵심 설계 결정 7가지

| # | 결정 | 이유 |
|---|---|---|
| 1 | 코어 하나, 입구 둘 | Chat과 무인은 질문을 누가 만드느냐만 다르다. Chat에서 검증한 분석 능력이 그대로 무인 감시 능력이 된다 |
| 2 | 조사는 ReAct 루프 | 무엇을 언제 볼지 미리 정할 수 없다. 결과를 보고 다음을 정하게 한다 |
| 3 | 계산은 시스템, 연결은 LLM | 통계·CNN·SQL은 코드가 한다. LLM은 결과를 읽고 해석·연결만 한다 |
| 4 | 검증기 통과분만 채택 | 근거 실재·사실 대조·신뢰도 규칙을 코드로 강제한다. 지어낸 문장은 채택되지 않는다 |
| 5 | 조치는 규칙표 + 권한별 승인 | 조치는 감사 대상이다. 등급을 LLM에 맡기지 않고 설명 가능한 규칙표로 정한다 |
| 6 | 등록은 현업, 확정된 것만 검색 | AI가 자동 등록하면 틀린 것이 쌓인다. 확정은 사람이 한다 |
| 7 | 조사규칙은 문서로 | 노하우의 주인은 현업이다. 코드가 아닌 문서라 직접 고치면 즉시 반영된다 |

### 4.3 기술 차별화 — 공모 심사 관점

**하나. 자동화가 별도 개발이 아니다.** 분석 코어를 Chat과 무인 감시가 공유한다. Chat 파일럿에서 엔지니어가 신뢰한 분석 능력이, 어댑터 하나를 붙이는 것만으로 24시간 무인 감시의 능력이 된다. 자동화 단계에서 분석 로직을 다시 만들지 않는다.

**둘. 수치 환각의 발생원을 제거했다.** 통계 계산, 공통성 분석, wafer map 분류, SQL 조회는 전부 코드가 수행하고 LLM에게는 그 결과만 넘긴다. LLM이 숫자를 만들어낼 자리가 구조적으로 없다.

**셋. 그럴듯한 오답이 채택되지 않는다.** 판단서는 구조화 출력으로 근거 인용을 강제하고, 검증기 5칙(스키마 / 근거 실재 / 사실 대조 / 신뢰도 규칙 / 공백 금지)이 코드로 검사한다. 실패하면 오류를 붙여 재생성하고, 계속 실패하면 판단 불가·사람 검토로 강등한다. 품질 시스템에서 그럴듯한 오답은 무응답보다 위험하다는 판단에서 나온 설계다.

**넷. 확산 비용이 구조적으로 낮다 — 공모 관점의 핵심.** 공정을 늘릴 때 코어를 다시 만들지 않는다. 조사규칙 문서(md)와 시스템지도만 그 공정 것으로 추가하면 된다. 2차년에 etch·CMP를 붙이면서 이 구조를 실증하고, 그 결과를 **공정별 조사규칙 템플릿 + 확산 표준안**으로 산출한다. 다른 조직이 이 과제 산출물을 받아 자기 공정에 적용할 수 있게 하는 것이 2차년의 명시적 목표다.

`commonality_analysis`가 특히 중요하다. 불량 wafer들이 공통으로 거친 설비를 찾는 것은 반도체 원인분석의 표준 기법인데, 이를 LLM의 즉석 SQL에 맡기지 않고 검증된 분석 함수로 제공해야 판단 품질이 안정된다.

### 4.5 조치 등급 체계

| 등급 | 정의 | 예 | 1차년 | 2차년 |
|---|---|---|---|---|
| L0 | 정보 제공 | 분석 답변, 리포트 | 즉시 | 즉시 |
| L1 | 알림·에스컬레이션 | 담당자 통보, 교대 브리핑 | 즉시 (규칙 기반) | 즉시 |
| L2 | 현장 영향 조치 **제안** | Lot Hold, 설비 점검 요청, dose 보정 | **전건 승인 후 실행** | 전건 승인 후 실행 |
| L3 | 자동 조치 | 되돌릴 수 있는 저위험 조치 | **개방하지 않음** | 화이트리스트 개별 승격 후 개방 |

모든 시나리오는 L2로 시작한다. 제안 → 사람 승인을 반복하며 시나리오별 승인율·오탐율이 쌓이면, 기준을 넘은 시나리오만 개별적으로 L3 승격을 심의한다. 승격 후에도 실행 내역은 전건 사후 리뷰한다. 설비 제어성 조치는 2차년에도 승인 대상이다.

## 7. 기대효과

### 7.1 정량

판정 업무 시간이 1인 하루 4시간에서 2시간으로 줄어드는 것을 기준으로 산정한다. 이는 GPU 수요등록 시 제출한 것과 동일한 기준이다.

```
[ (4h/8h) − (2h/8h) ] × 연봉 80,000,000원 × 1,000명 = 연 200억 원
```

| 구분 | 값 |
|---|---|
| 연간 기대효과 (확산 완료 후) | 200억 원 |
| 연간 투자 | 347,794,165원 |
| **연간 기준 ROI** | **약 57.5배** (회수 약 6.3일) |
| 2개년 총투자 | 695,588,330원 |
| **총투자 기준 회수 기간** | **약 12.7일** (완전 가동 1년 효과 기준) |

**연차별 효과 인식** — 1차년은 포토 1개 공정 파일럿 구간이므로 효과를 전면 산정에 넣지 않고 실측 구간으로 둔다. 위 200억은 3개 공정 확산 후 1,000명 전면 적용을 전제로 한 값이다.

**민감도** — 목표를 절반만 달성해도 투자 대비 효과는 크게 남는다.

| 목표 판정 시간 | 절감 비율 | 연간 기대효과 | 연간 ROI |
|---|---|---|---|
| **2.0시간 (기준)** | 25.0% | 200억 | **57.5배** |
| 2.5시간 | 18.8% | 150억 | 43.1배 |
| 3.0시간 | 12.5% | 100억 | 28.8배 |
| 3.5시간 | 6.3% | 50억 | 14.4배 |

하루 4시간에서 3.5시간, 즉 30분만 줄어도 ROI 14배다.

**검증 방법** — 가동 후 건당 처리 시간을 로그로 실측하고 골든 시나리오 정답률을 함께 측정해 분기 단위로 보고한다. 산정치와 차이가 나면 그때 조정한다.

### 7.2 정성 · 파급

야간·주말 대응 공백이 사라진다. 같은 현상에 같은 판단이 나와 엔지니어 간 편차가 줄어든다. 판단 근거가 남아 감사 대응이 가능해진다. 노하우가 문서와 등록 자산으로 남아 담당자 교체에 흔들리지 않는다.

**확산 파급** — 2차년 산출물인 확산 표준안(조사 코어 + 공정별 조사규칙 템플릿 + 골든셋 구축 절차)은 다른 공정과 다른 조직이 그대로 가져다 쓸 수 있는 형태로 만든다. 코어를 다시 개발하지 않고 조사규칙 문서만 추가하면 되는 구조라 확산 비용이 낮다. 다만 확산 시점의 추가 효과는 대상 조직·인원이 정해진 뒤 산정하며, 지금 이 지원서에는 수치로 넣지 않는다.

| R7 | 담당 인력의 학습 곡선 | 일정 지연 | 1차년 1~2Q를 작게 유지, 프리빌트에서 커스텀으로 점진 전환 | 1차년 |
| R8 | **2차년 확산이 코어 수정을 요구** | 확산 비용 가정이 무너짐 | 1차년 설계 단계부터 공정 의존 로직을 조사규칙 문서로 분리. 5Q etch 확산에서 코어 변경 0을 통과 조건으로 검증 | 2차년 5Q |

R1과 R5는 발생 시 과제 진행 자체를 멈추고 재검토해야 하는 항목이다. R8은 2개년 과제로 만들면서 새로 생긴 리스크이며, 5Q의 통과 조건("코어 변경 0")이 그 자체로 검증 장치다.

## 9. 성과 검증 방안

### 9.1 회귀 게이트 — 배포를 막는 자동 장치

프롬프트·모델·임베딩·색인을 바꿀 때마다 골든셋 회귀 러너를 돌린다. 통과하지 못하면 배포하지 않는다. 금지 조치(fail_criteria)를 건드리면 즉시 실패 처리한다. 개선이 감(感) 싸움이 되지 않게 하는 유일한 장치다.

### 9.2 검증 항목

| 검증 | 방법 | 통과 기준 | 주기 |
|---|---|---|---|
| 판단 정확도 | 골든셋 회귀 러너 | 기준선 대비 하락 없음 | 변경 시마다 |
| 검색 품질 | `eval_recall.py` — recall@10, MRR, precision@3 | 직전 측정값 대비 하락 없음 | 변경 시마다 |
| 환각 차단 | 검증기 날조·왜곡·과장 3종 재현 테스트 | 3종 모두 차단 | 변경 시마다 |
| 권한 통제 | 승인 없이 L2 조치 시도 | 변경 0건 (거부) | 월 1회 |
| 조회 계정 통제 | 조회 계정으로 UPDATE 시도 | 권한 거부 | 월 1회 |
| 그림자 일치율 | AI 판단 대 엔지니어 판단 비교 (조치 미실행) | 1차년 2Q에서 기준선 확보 | 1차년 2Q |
| 확산 무변경 | etch·CMP 추가 시 코어 diff | **코어 변경 0** | 2차년 5Q·6Q |
| 자동 실행 감사 | 자동조치 로그 전건 리뷰 | 오판율 측정·공개 | 2차년 7Q~ |

### 9.3 운영 지표 (월간 리포팅)

건당 처리 시간, 이벤트 처리 누락 건수, 조치 승인율·반려율, GPU 가동률, 등록된 Inform Note 건수.

## 10. 선행 추진 실적

이 과제는 백지에서 시작하지 않는다. 설계와 선행 검증을 이미 마친 상태다.

| 구분 | 완료 내용 |
|---|---|
| 설계 문서 | 시스템설계서, 상세 구축 로드맵, Tool 카탈로그, 그라운딩 설계, 조사규칙 5종, 구현명세서 등 **31종** |
| 구현 | LangGraph 조사 코어 스켈레톤 실행 확인, 검증기 5칙 구현, prod 백엔드 4종 |
| 평가 | 골든 시나리오 4건 + 회귀 러너 구축, 회귀 검출 동작 확인. 검색 **recall@10 = 0.500 실측** (골든 4건 / 색인 50건) |
| DB | 테스트 VM에 **PostgreSQL 16.14 + pgvector 0.8.1** 구축, 스키마·가드·평가 동작 확인. halfvec 사용 확정 |
| 인프라 | **GPU 수요등록 완료** (H100 20장), BIG VM 5대 산출근거 제출, 스토리지 신청 포함 |

즉 **설계·스켈레톤·평가 체계·DB까지는 이미 서 있고, 이 과제는 그 위에 실데이터와 실도구를 연결해 두 공정 더 확산하는 단계**다. 공모에서 흔히 문제가 되는 "될지 안 될지 모르는 구간"이 이미 지나 있다.
