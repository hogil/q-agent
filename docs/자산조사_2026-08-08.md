## 1. 선행 프로토타입 A — `D:\project\failure_agent`

**불량 이미지 분석 에이전트 + Streamlit 웹앱.** 이미지를 넣으면 갤러리에서 닮은 과거 사고를
찾고, 그 사고 메타데이터를 근거로 LLM 이 인용을 달아 설명한다.

### 구현된 것
| 항목 | 내용 |
|---|---|
| Agent | LangGraph `create_react_agent` + 도구 2종 (이미지 유사 검색 / 사고 이력 조회) |
| 이미지 모델 | ConvNeXt V2-Base (FCMAE 사전학습) + 128차원 projection head, cosine 유사도 |
| 지식 | 43개 불량 class 별 `meta.json` — 사고일자·근본원인·의심설비·recipe 이슈·조치 |
| 인용 강제 | LLM 답변에 `[meta.field]` 인라인 인용. 클릭하면 우측 패널에서 해당 필드 하이라이트 |
| UI | 업로드·샘플 버튼 / 첨부 vs Top-1 나란히 / 유사도 점수·confidence / 43 class 갤러리 / 스트리밍 답변 / 유사 이미지 5열 |

### 실측 (출처 `docs/ARCHITECTURE.md`)
- 임베딩 군집 **AMI 0.956 · ARI 0.860 · 노이즈 0.52%**
- 학습 데이터 **43 class × 30장 = 900 wafer**
- ⚠ **군집 품질 지표이지 진단 정답률이 아니다.** "판정 정확도"로 바꿔 부르면 허위가 된다

### 없는 것
시계열·이상탐지, DB 조회, 배포 후 정확도·처리시간, 골든셋 회귀 배치.

### 실행
`python run.py` (자동으로 의존성 설치 → gallery 생성 → Streamlit 기동 → 브라우저 오픈).
로컬에 `images/` 215장 · `embeddings/gallery.npz` · `samples/` 5장 · `.env` 전부 있어 바로 뜬다.
**외부 LLM API 키가 필수다** (또는 `LLM_PROVIDER=ollama`). 키 없으면 앱이 시작되지 않는다.

- 코퍼스 60 → 4,427청크 **2.4배 확장 뒤에도 0.962 · 지연 1.29초** 유지
- 색인 규모 **5,291청크 / 103문서** (PostgreSQL 16 + pgvector)
- **BM25 등가중(1.0)이 최적임을 실측으로 확인** — 하이브리드 가중치를 감으로 정하지 않았다

### 쓸 때 주의 (세 가지 안전판)
1. **모델이 다르다.** 이 실측은 `bge-m3` + `bge-reranker-v2-m3` 기준이고, 본 과제는
   `Qwen3-Embedding-8B` + `Qwen3-Reranker-8B` 로 교체 예정이다.
   **"Qwen3 로 hit@1 0.957 을 냈다"는 거짓**이 된다
2. **`recall@10 = 0.500` 과 섞지 마라.** 그건 Q-Agent 골든셋(4건/색인 50건) 값이다.
   다른 시스템·다른 코퍼스라 한 문장에 나란히 놓으면 오독된다
3. 라우터·답변 LLM 은 외부 상용 API 를 쓴다 (ollama fallback 있음).
   사내 문서에 벤더명을 쓰지 않는다

## 3. 사내 공용 RAG 의 실제 사정

사용자 확인 사항. **"공용 RAG 는 아무것도 안 된다"는 틀린 서술이다.**

| 항목 | 사실 |
|---|---|
| 텍스트·사내 공용문서 적재 | **사내 RAG system API 로 가능하다** |
| 구성 | **디폴트 고정** — BM25 + bge-m3 + 기본 reranker |
| 우리가 고를 수 있는 것 | **tokenizer 정도가 전부**로 보인다 |
| 못 하는 것 | 반도체 사전 등록, 용어 병기(ACI→세정 후 계측), 한국어 형태소 색인, 메타 필터(eqp_id·공정·기간), 임베딩·리랭커 교체, recall 지표 열람 |

**서술 방향** — "적재는 사내 API 로 되지만, 검색 품질을 좌우하는 손잡이가 tokenizer 하나뿐이다."
이게 "전부 막혔다"보다 정확하고, 사내 RAG 를 아는 사람에게 반박당하지 않는다.

**부수 효과(유리)** — 텍스트 적재를 사내 RAG 에 얹으면 중복 투자가 없다는 논거가 된다.
그 경우 자체 구축의 초점은 **이미지 검색과 도메인 특화 재순위**로 좁혀진다.
다만 사용자도 "~일 수도 있다"로 말한 미확정 사항이라 단정해 쓰지 않는다.

## 4. 명명 규칙 (현업이 바로 알아보는 자리)

- **설비명에는 하이픈이 없다.** `PHO-D03` 같은 표기는 존재하지 않는다 → `PHOD03`
- **하이픈·언더바가 붙는 것은 recipe 명이다** (예: `PH_CD_A01-3`). 분절 사고는 여기서 더 크게 난다
- 사전 등록 대상은 설비 ID 하나가 아니다 — **EQP · STEP · recipe · 계측 항목 · 불량 유형**까지
  규칙으로 학습시켜 **어떤 것도 토큰으로 떨어지지 않게** 하는 것이 요지다

일반 토크나이저는 `PHOD03` 을 `PHO/D/03` 으로, `PH_CD_A01-3` 을 구분자마다 조각낸다.
**쪼개지는 순간 그 문서는 검색에서 사라진다.** 공용 RAG 에서 고를 수 있는 게 tokenizer 뿐이라면
사전이 유일한 손잡이가 된다.

## 5. 근거 체인 — 이미지에서 원본 문서까지

사용자가 설명한 실제 동작 사슬. **LLM 이 지어낸 것이 하나도 섞이지 않는다.**

```
① 이미지 투입      불량 이미지를 넣는다
② 유사 사고 검색   이미지 스토리지에서 임베딩 유사도로 닮은 과거 사고를 찾는다
③ 메타 키 매칭     찾은 이미지의 파일 경로·메타데이터를 키로 삼아 사고를 특정한다
④ RDB 실데이터     그 키로 사고 이력 RDB 를 조회한다.
                   이 표는 LLM 이 문서를 읽고 만든 것이 아니라 현업이 직접 기입한 원본이다
⑤ 원본 문서 매칭   RDB 의 경로로 사고 보고서 원문까지 찾아 docling·OCR 로 읽고,
                   LLM 이 그 원문을 근거로 추가 정보를 설명한다
```

**왜 결정적인가**
- 유사도는 후보만 좁힌다. **확정은 키 조회**가 한다 — 벡터 검색의 모호함이 판정에 안 들어온다
- 사고 정보의 출처가 **사람이 기입한 RDB** 다. LLM 요약본이 아니라 감사에서 원본을 그대로 댈 수 있다
- 문서는 경로로 매칭해 **원문을 읽는다.** 요약을 다시 요약하지 않는다
- 판단 근거가 이미지 → 키 → 원본 데이터 → 원본 문서로 **끝까지 실물에 닿아 있다**

대부분의 AI 과제가 "RAG 붙였습니다"에서 끝나는 데 반해, 이건 **환각이 들어올 자리를 구조적으로
막은 설계**다. 지원서 TECH 항목의 결정타인데 **아직 본문에 안 들어갔다.**

## 6. `failure_agent` 의 meta.json 은 생성된 데모 데이터다 (기밀 아님)

웹앱 화면을 지원서에 넣어도 되는지 판단하려고 직접 확인했다. **실제 사내 데이터가 아니다.**

**근거 — 같은 레코드 안에서 수치가 어긋난다**
- `BrokenRing` : `yield_impact` 필드는 `27% lot yield loss` 인데 같은 레코드 `description` 은 `45%`
- `Center_bank_boundary` : 필드 `47%` / 설명 `18%`

**원인과 조치가 짝이 안 맞는다**
- `BrokenRing` — 원인은 "Plasma etch endpoint 실패", 혐의 설비는 etch 챔버인데
  **조치가 "Slurry/chemical filter 교체"**(CMP 조치)다. 공정 단계는 또 "Wet Clean" 으로 적혀 있다
- `Center_bank_boundary` — 원인은 spin coater chuck + dicing saw 인데 **조치가 "Probe card replacement"**

**설비명이 전부 공개된 상용 장비 모델명이다** — AMAT Centura, TEL CLEAN TRACK ACT, DISCO DAD3350,
LAM Kiyo. 사내 고유 설비 코드가 아니다. `FAB5-LINE-C` 도 자리표시자 패턴이다.

실제 사고 데이터라면 한 레코드에서 수율이 두 값으로 갈리거나 etch 원인에 CMP 조치가 붙지 않는다.
wafer 이미지도 공개 데이터셋(WM-811K 계열 패턴명)으로 보인다.

**캡쳐 판단** — 넣어도 된다. 다만 **meta.json 전문이 크게 박힌 화면은 피한다**
(심사위원이 확대해 "27% 인데 왜 설명은 45% 지?"를 보면 손해).
추천 컷 ① 인용 chip → split panel 하이라이트 ② 유사 이미지 갤러리 ③ 첨부 vs Top-1 + 유사도 점수.

## 7. 학습 대상 — 실제로 무엇을 학습하는가

"시스템 프롬프트 갈고닦기"로 끝나면 TECH 의 "개선 수행 과정"에 답이 안 된다.
학습 대상은 세 층으로 나뉜다.

### 검색기 (효과가 제일 크고 제일 만만하다)
| 대상 | 데이터 | 왜 |
|---|---|---|
| Embedding 파인튜닝 | (질의, 정답 Inform Note) 쌍 + 틀린 후보 | 사내 문서는 "CD 상승"이 수백 건이라 일반 임베딩은 다 비슷하게 본다 |
| Reranker 파인튜닝 | (질의, 문서, 채택/기각) 라벨 | recall@10 보다 **precision@3** 에 직결. 엔지니어가 실제로 보는 건 상위 3건 |
| 질의 재작성 | 원질문 → 실제로 통한 질의 | "어제 그 문제" 를 검색 가능한 질의로 |

틀린 후보는 **회귀 러너가 자동으로 만든다** — recall@10 에서 놓친 케이스가 곧 그것이다.
데이터 수집 파이프라인이 이미 있는 셈이다.

### 판단 LLM (프롬프트 튜닝이 아니라 궤적 학습)
- **도구 호출 궤적** — "어떤 상황에 어떤 도구를 부르는가". 골든셋 + 실제 조사 로그의 성공 궤적
- **조사 종료 판단** — 언제 그만 부를지. 과소하면 근거 부족, 과다하면 비용. 의외로 제일 어렵다
- **판단서 형식 준수** — 검증기 5칙 탈락 사례가 그대로 negative 가 된다
- **선호학습** — 엔지니어 채택/수정/기각 피드백이 그대로 선호쌍.
  "살아있는 시스템"이라는 주장의 유일한 실물 근거

즉 **검증기 탈락 로그와 엔지니어 반려 로그가 곧 학습 데이터**다. 별도 라벨링 비용이 안 든다.

### Vision (LLM 이 못 하는 영역이라 따로 간다)
이미 하고 있는 것 — `failure_agent` 의 ConvNeXt V2 대조학습(AMI 0.956)이 그 증거다.
LLM 은 그 **결과만 텍스트로 받는다.** "계산은 코드, 연결은 LLM" 원칙이 여기서 나온다.

### ⚠ 지원서에 쓸 때의 제약
정본 `docs/01_과제지원서_본문.md` 에 **`SFT`·`DPO`·`LoRA`·`hard negative` 문자열이 없다.**
쓸 수 있는 것은 정본 어휘뿐이다 — `:51` "검색기 파인튜닝, 선호학습" / `:246` "재학습 월 4회 루틴화".
(10회차에 두 모델이 DPO·LoRA 를 넣자고 했다가 정본 확인 후 기각됐다.
`distractor` 는 `ax_award/CLAUDE.md §0-3` 사실표 원문이라 쓸 수 있다.)

### 한글 문서 생성의 함정 3가지
1. **한글 글꼴은 `w:eastAsia` 를 직접 넣어야 적용된다.** `run.font.name` 은 `w:ascii`/`w:hAnsi`
   만 쓰고, 한글은 East Asian 으로 분류돼 테마 글꼴로 렌더된다
2. **중첩 표가 든 행은 Word 가 페이지 분할을 못 한다.** 페이지마다 표를 따로 만들어야 한다
3. **`✕`(U+2715)·`−`(U+2212) 는 맑은 고딕에 글리프가 없어 □ 로 깨진다.** `×`·`-` 를 쓴다
