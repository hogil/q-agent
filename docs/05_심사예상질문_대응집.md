# 심사 예상질문 대응집

**반도체 품질 이상감지·판단 AI Agent Orchestration 구축** · 과제 지원서 붙임 4

작성일 2026-08-07

---

## 이 문서를 쓰는 법

질문마다 **한 줄 답**과 **근거**를 나눠 두었다. 발표 자리에서는 한 줄 답만 말하고, 파고들면 근거를 편다. 근거에 없는 숫자는 말하지 않는다. 모르는 것은 "확인해서 회신하겠습니다"로 닫는 편이 낫다 — 이 과제의 핵심 주장 자체가 "확인된 데이터로만 말한다"이기 때문에, 발표자가 추측으로 답하면 그 주장이 무너진다.

## A. 필요성 · 대체 가능성

### A1. 사내 LLM API를 쓰면 되지 않나?

**한 줄** — 사내 API는 판단에 필요한 사내 DB 조회와 이미지 판독을 하지 못하고, 우리 데이터로 정확해지는 경로 자체를 제공하지 않는다.

**근거 다섯 가지**

| # | 논거 | 내용 |
|---|---|---|
| 1 | 판단 정확도의 구조 | 판단은 사내 DB·trend·image를 도구로 불러 대조하는 과정이다. API는 문장 생성만 한다 |
| 2 | 검색기 파인튜닝 미제공 | 사내 용어·설비 ID로 임베딩과 리랭커를 학습시킬 수 없다 |
| 3 | SFT·선호학습 불가 | 엔지니어 피드백을 모델에 반영하는 경로가 없다. 쓸수록 좋아지는 구조가 성립하지 않는다 |
| 4 | 에이전트 토큰 구조 | 도구 호출이 건당 5~15회 왕복한다. 호출당 과금·지연 구조에서는 감당이 안 된다 |
| 5 | 재현성·데이터 경계 | 판정 이력에 모델 버전을 함께 기록해야 감사에 답할 수 있다. 외부 API는 버전을 고정할 수 없다 |

### A2. 사내 공용 RAG로 대신하면 되지 않나?

**한 줄** — 일곱 가지 항목이 모두 불가하거나 대부분 불가하다. 특히 설비 ID와 사내 용어를 다루지 못하는 것이 결정적이다.

**근거**

| # | 필요한 것 | 공용 RAG |
|---|---|---|
| 1 | DB 기준정보·trend·image를 함께 읽어 판단 | 불가 |
| 2 | 사내 용어 병기 (ACI → 세정 후 계측) | 불가 |
| 3 | 설비 ID 토큰 보호 (PHO-D03을 쪼개지 않고 통짜로) | 불가 |
| 4 | 한국어 형태소 색인 + 조사 제거 | 대부분 불가 |
| 5 | 메타 필터 (설비·공정·기간으로 좁히기) | 대부분 불가 |
| 6 | 임베딩·리랭커 교체 | 불가 |
| 7 | recall@k 지표 열람 | 불가 |

3번을 부연하면 이렇다. `PHO-D03`을 일반 색인기가 처리하면 `PHO`와 `D`와 `03`으로 쪼갠다. 그러면 `PHO-D01` 문서도 같이 걸린다. 설비를 특정하지 못하는 검색은 품질 판단에 쓸 수 없다.

### A3. BI 대시보드를 더 잘 만들면 되지 않나?

**한 줄** — 대시보드는 사람이 봐야 할 화면을 늘린다. 지금 문제는 화면이 부족한 게 아니라 여러 화면을 사람이 이어붙여야 한다는 것이다.

### A4. SPC 알람이 이미 있는데 왜 또 만드나?

**한 줄** — SPC 알람은 "이상이다"까지 알려준다. 이 시스템은 "왜 그런가, 무엇을 해야 하나"에 답한다. SPC 알람은 대체 대상이 아니라 이 시스템의 트리거 입력으로 그대로 쓴다.

## B. 기술 · 신뢰성

### B1. LLM이 틀린 판단을 하면 어떻게 되나?

**한 줄** — 틀린 판단이 채택되지 않도록 판단 단계에서 한 번, 조치 단계에서 또 한 번 막는다.

**판단 단계 — 검증기 5칙 (코드가 검사)**

| 규칙 | 무엇을 막나 |
|---|---|
| 스키마 | 정해진 형식이 아니면 거부 |
| 근거 실재 | 존재하지 않는 증거를 인용하면 거부 |
| 사실 대조 | 도구가 돌려준 원문에 없는 수치를 쓰면 거부 |
| 신뢰도 규칙 | High를 주장하려면 근거 3개 이상, 반증 0 |
| 공백 금지 | 가설이 없으면 무엇이 부족한지를 명시하게 강제 |

실패하면 오류를 프롬프트에 붙여 재생성한다. 계속 실패하면 "판단 불가, 사람 검토"로 강등한다.

**조치 단계 — 등급표 + 승인 게이트**

현장에 영향을 주는 조치(L2)는 승인 없이는 실행 자체가 거부된다. 그래프가 멈추고 승인을 기다린다. 승인이 몇 시간 뒤에 와도 체크포인터가 그 지점을 보존하므로 이어서 실행된다.

**세 번째 방어선** — 회귀 게이트. 프롬프트·모델·색인을 바꿀 때마다 골든셋 회귀 러너를 돌려 통과하지 못하면 배포하지 않는다.

### B2. 그래도 숫자를 지어내면?

**한 줄** — LLM이 숫자를 만들 자리가 구조적으로 없다.

통계 계산, 공통성 분석, wafer map 분류, SQL 조회는 전부 도구(코드)가 수행한다. LLM은 도구가 돌려준 JSON을 읽고 해석·연결만 한다. 그리고 검증기 3번(사실 대조)이 "원문에 없는 수치"를 코드로 잡아낸다. 이 두 가지가 겹쳐 있다.

### B3. 기간계 DB에 부하를 주는 것 아닌가?

**한 줄** — 운영계에 직접 붙지 않는다. 정보계(DW·ODS)를 경유하고, 조회 전용 계정으로만 접근한다.

가드는 네 겹이다. 조회 전용 계정과 최소 스키마 권한, 에이전트 전용 뷰, 쿼리 가드(SELECT 전용 검증·행 수 제한·statement_timeout), 그리고 사건당 캐시. 검증 항목에도 "조회 계정으로 UPDATE 시도 → 권한 거부"를 넣어 월 1회 확인한다.

### B4. AI가 마음대로 설비를 세우면?

**한 줄** — 조치 등급을 LLM이 정하지 않는다. severity × confidence 규칙표가 정한다.

등급이 규칙표에서 나오는 이유는 조치가 감사 대상이기 때문이다. 감사에서 "왜 이 조치를 L1으로 봤나"에 답하려면 설명 가능한 규칙이어야 한다. 그리고 L3(자동 조치)는 이 과제 범위 밖이다. 시나리오별로 정확도를 실측한 뒤 개별 심의로 승격한다.

### B5. 왜 대형 LLM 하나가 중심인가? 작은 모델 여럿이 낫지 않나?

**한 줄** — 판단·코딩·도구 호출을 한 모델이 맡아야 프롬프트 캐시를 공유하고 도구 선택이 일관된다.

역할 분기는 시스템 프롬프트로만 한다. 같은 엔드포인트를 쓰기 때문에 앞부분 고정 프롬프트가 캐시에 걸린다. 모델을 나누면 이 이득이 사라지고, 모델마다 도구 호출 품질이 달라 판단이 흔들린다.

### B6. 오픈 모델을 쓰다가 더 좋은 게 나오면?

**한 줄** — 모델 교체를 전제로 설계했다. 회귀 게이트가 그 판단 기준이다.

모델·임베딩·리랭커는 서빙 뒤에 있고 도구 계약(입출력 스키마)은 바뀌지 않는다. 교체 시 골든셋 회귀를 돌려 기준선 대비 하락이 없으면 배포한다. 모든 판정 이력에 모델 버전을 기록하므로 어느 버전이 어떤 판단을 했는지 추적된다.

## C. 자원 · 비용

### C1. H100 20장이 정말 필요한가?

**한 줄** — 사내 GPU 수요등록 시스템이 산출한 값이 20.1장이다. 임의로 정한 숫자가 아니다.

등록 5건의 합계 B300 10.05를 H100으로 환산(계수 1:2)하면 20.1장이다. 배분은 서빙 판단 LLM 12장, 고정밀 VLM 5장, 경량 VLM·검색기 2장, 회귀평가 1장으로 남는 슬롯이 0이다.

### C2. 12장을 서빙에 쓰는 근거는?

**한 줄** — FP8 가중치가 약 743GB이고 H100은 카드당 80GB이므로 적재에만 최소 10장이 필요하다. 여기에 KV 캐시와 동시 처리 여유를 더해 12장이다.

> ★ 기존 GPU 제출본 서술형 '적합성' 필드에 `적재 8장`으로 적힌 부분이 있다. 이는 H200(141GB) 기준 초안이 남은 것으로, H100 기준으로는 `적재 최소 10장`이 맞다. 결론(서빙 12장·총 20장)은 바뀌지 않는다. 심사 전에 문구를 정정할 것.

### C3. 학습할 때 서비스가 멈추나?

**한 줄** — 멈추지 않는다. 학습 모드에서 16장을 전환하고 경량 서빙 4장을 유지한다.

### C4. VM 5대가 과한 것 아닌가?

**한 줄** — 운영 2대(HA), 데이터 2대(주·복제), 학습 1대다. 어느 하나를 빼면 이중화나 학습 분리가 깨진다.

train01을 따로 둔 이유는 웨이트 병합을 GPU 노드에서 하면 GPU 슬롯을 회당 3~5시간 잡아먹기 때문이다. 월 4회 학습이므로 이 분리만으로 GPU 시간이 상당히 절약된다.

### C5. 관리형 DB를 쓰면 더 싸지 않나?

**한 줄** — 관리형 신청은 반려되었다. 직접 설치로 확정했고, 오히려 스펙이 올라가고 비용이 줄었다.

관리형은 32코어·128GB였고, data01/02 직접 설치는 64코어·1,024GB다. 인덱스를 전량 메모리에 올릴 수 있다. pgvector 버전도 자유롭게 고를 수 있어 실측한 0.8.1에서 halfvec을 쓴다 — 벡터 색인 크기가 절반이 된다.

## D. 효과 산정

### D1. 연 200억은 너무 낙관적 아닌가?

**한 줄** — 산식이 단순해서 검증 가능하다. 그리고 목표를 절반만 달성해도 투자 대비 효과는 크게 남는다.

```
[ (4h/8h) − (2h/8h) ] × 연봉 80,000,000원 × 1,000명 = 연 200억 원
```

| 목표 판정 시간 | 절감 비율 | 기대효과 | ROI |
|---|---|---|---|
| **2.0시간 (기준)** | **25.0%** | **200억** | **57.5배** |
| 2.5시간 | 18.8% | 150억 | 43.1배 |
| 3.0시간 | 12.5% | 100억 | 28.8배 |
| 3.5시간 | 6.3% | 50억 | 14.4배 |

하루 4시간에서 3.5시간, 즉 30분만 줄어도 ROI 14배다. 그리고 이 산정은 GPU 수요등록 때 제출한 것과 동일한 기준이라 두 문서가 서로 어긋나지 않는다.

### D2. 그 효과를 어떻게 검증하나?

**한 줄** — 가동 후 건당 처리 시간을 로그로 실측하고 분기 단위로 보고한다. 산정치와 차이가 나면 그때 조정한다.

함께 측정하는 것 — 골든 시나리오 정답률, 이벤트 처리 누락 건수, 조치 승인율·반려율, GPU 가동률, 등록된 Inform Note 건수.

### D3. 정답률 목표가 왜 없나?

**한 줄** — 기준선을 아직 실측하지 않았기 때문이다. Phase 0 그림자 운영에서 측정한 뒤 목표치를 확정하고, 그 값을 회귀 게이트로 고정한다.

임의의 퍼센트를 적으면 그 숫자를 근거로 심사를 통과한 뒤 실측치가 다를 때 설명할 방법이 없다. 지금 제시할 수 있는 실측치는 검색 recall@10 = 0.500 하나뿐이며(골든 4건 / 색인 50건), 이건 그대로 적었다.

## E. 실행 가능성

### E1. 이런 걸 만들어 본 적이 있나?

**한 줄** — 설계·스켈레톤·평가 체계·DB까지는 이미 서 있다. 이 과제는 그 위에 실데이터를 붙이는 단계다.

| 구분 | 완료한 것 |
|---|---|
| 설계 문서 | 시스템설계서, 상세 구축 로드맵, Tool 카탈로그, 그라운딩 설계, 조사규칙 5종, 구현명세서 등 31종 |
| 구현 | LangGraph 조사 코어 스켈레톤 실행 확인, 검증기 5칙 구현, prod 백엔드 4종 |
| 평가 | 골든 시나리오 4건 + 회귀 러너 구축, 회귀 검출 동작 확인, recall@10 = 0.500 실측 |
| DB | PostgreSQL 16.14 + pgvector 0.8.1 구축, 스키마·가드·평가 동작 확인 |
| 인프라 | GPU 수요등록 완료, BIG VM 5대 산출근거 제출 |

### E2. 12개월이 현실적인가?

**한 줄** — 단계를 기간이 아니라 통과 조건으로 관리한다. 통과하지 못하면 다음 단계로 가지 않는다.

Phase 0(1~2개월)에서 그림자 운영으로 일치율 기준선을 잡지 못하면 Phase 1을 시작하지 않는다. 일정이 밀리는 대신 검증되지 않은 것이 현장에 나가지 않는다. 확산(Phase 4)은 코어를 그대로 두고 조사규칙 문서만 추가하는 구조라 뒤로 갈수록 빨라진다.

### E3. 담당자가 바뀌면 어떻게 되나?

**한 줄** — 조사 노하우를 코드가 아니라 문서(조사규칙 md)로 두었다. 현업이 직접 고치면 즉시 반영된다.

판단 이력도 근거와 모델 버전을 함께 남기므로, 새 담당자가 과거 판단을 그대로 따라 읽을 수 있다.

### E4. 엔지니어들이 안 쓰면?

**한 줄** — 그 위험을 일정에 넣었다. Phase 1의 통과 조건이 "엔지니어가 실제로 쓰는가"다.

반려율과 질문 재사용률을 측정한다. 쓰지 않으면 적용 공정을 줄이고 다시 파일럿한다. 오탐 알림 남발(R4)도 같은 이유로 관리 대상이며, 어댑터 앞단의 이벤트 그룹핑·중복 제거가 여기에 대한 대응이다.

### E5. 등록을 아무도 안 하면?

**한 줄** — 이 시스템의 가장 현실적인 실패 모드다. 그래서 Phase 0부터 등록을 습관으로 만든다.

사고가 종결되면 AI가 Inform Note 초안을 만들어 엔지니어 승인 큐에 올린다. 백지에서 쓰는 게 아니라 초안을 고치는 일이라 부담이 작다. 등록 건수를 월간 지표로 리포팅해 선순환이 도는지 확인한다.

## F. 보안 · 거버넌스

### F1. 데이터가 밖으로 나가지 않나?

**한 줄** — 사내망 안에서 완결된다. 모델도 사내 GPU에서 서빙한다. 외부 API를 쓰지 않는 것이 이 구성을 택한 이유 중 하나다.

### F2. 감사에 어떻게 대응하나?

**한 줄** — 모든 판정에 근거 인용, 신뢰도, 사용 모델 버전을 함께 기록한다.

LangGraph 체크포인터가 매 단계 스냅샷을 남기므로 "어떤 데이터를 보고 어떤 추론으로 어떤 결론을 냈는지" 전체 경로가 추적된다. 조치 실행 로그(누가·언제·무엇을 승인)는 영구 보존하고 분기 리뷰한다.

### F3. 권한은 누가 정하나?

**한 줄** — 거버넌스가 권한 정책을 소유하고, L3 승격 심의도 거버넌스가 주관한다.

승인 권한은 조치 종류로 나눈다. dose 보정은 엔지니어, 설비 정지는 상위 승인이다.
