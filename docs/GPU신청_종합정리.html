3. 산출 공식과 역검증 화면값에서 역산해 복원 · 이번에 다시 돌려 확인

수요등록 시스템은 계산식을 공개하지 않는다. 입력을 바꿔가며 화면 산출값을 관찰해 아래 공식을 복원했다. 복원된 공식이 맞는지 이번에 5건 전부를 다시 계산해서 확인했다.

복원한 공식

TOKEN형  연산량 = 모델크기 × 토큰수 × epoch × K계수   (K: MoE 3 / dense 6)
STEP형   연산량 = 모델크기 × step수 × eq계수 × K_step   (LLM Agent Standard K_step = 4000, K계수 없음)
장수 환산 B300 = 연산량(E) ÷ (137 × 1회 dev 일수)
dev 일수  1회 dev 일수 = release 주기 ÷ dev 횟수
스펙 계수 H100 = B300 × 2  /  A100 = B300 × 4

E = 1018. 137은 "B300 1장이 하루에 처리하는 연산량(E)"에 해당하는 상수로, 화면값에서 되찾은 반올림 값이다.

판정 — 공식은 맞다

연산량은 5건 전부 화면값과 정확히 일치했다. 공식의 뼈대(모델크기 × 학습량 × epoch × K, STEP은 eq × 4000)는 확실히 맞다.

B300 환산은 4건이 소수 둘째 자리까지 일치하고 [1]만 4.88 대 4.89로 0.01 차이가 난다. 원인은 나눗수 137이 화면값에서 되찾은 반올림 상수라서다(136.6~136.9 사이 어디여도 화면상 같은 값이 찍힌다). 합계는 10.04 대 10.05인데 H100 환산은 양쪽 다 20.1장이라 신청 근거는 흔들리지 않는다.

실무적 의미: 재신청·항목 추가 때 이 공식으로 미리 계산하면 시스템에 넣기 전에 장수를 알 수 있다. 소수 둘째 자리는 ±0.01 오차를 감안한다.

이번에 발견 — 제출 텍스트의 "적재 8장"은 H100 기준으로 안 맞는다

3필드 '적합성'에 "FP8 가중치 ~743GB(적재 8장/서빙 12장/학습 16장+)"이라고 적혀 있다. 그런데 H100은 장당 80GB다. 743 ÷ 80 = 9.3이므로 가중치만으로도 최소 10장이 필요하고, 8장(640GB)에는 애초에 안 올라간다. "8장"은 장당 141GB 카드를 가정하던 초안 시절 숫자가 남은 것이다.

H100 기준으로 고쳐 쓰면: 가중치 적재 최소 10장(800GB) / 서빙 12장(960GB = 가중치 743 + KV·활성 217) / 학습 16장. 서빙 12장이라는 결론은 그대로 맞고, 중간의 "적재 8장" 한 줄만 틀렸다. 심사위원이 산수를 따라오면 지적당하는 자리이므로 제출 텍스트에서 이 줄만 수정하면 된다.

4. 전 모델 자체 학습 체계판단 LLM·이미지·검색 모델을 각각 사내 데이터로 개별 학습. 피드백(채택/수정/기각) 자동 축적 → 정기 반영, 검증 통과 버전만 배포

H100은 카드당 80GB다. 743 ÷ 80 = 9.3 → 최소 10장이어야 가중치가 올라간다. 8장 = 640GB로는 물리적으로 안 올라간다. 이 "8"은 H200(141GB) 기준으로 쓴 예전 초안의 숫자가 그대로 남은 것이다.

16.2 "왜 [2]와 [5]가 중복이 아닌가" — 가장 나오기 쉬운 질문

둘 다 "이미지"라는 단어가 붙어서 중복으로 보이지만, 하는 일이 완전히 다르다.

[2] Qwen3.5-397B = 생성 모델. 이미지를 보고 판정 텍스트를 만든다. ("중앙부 edge 결함, 8시 방향 집중")
[5] Qwen3-VL-Embedding = 임베딩 모델. 이미지를 벡터로 바꿔 비슷한 과거 사례를 찾아올 뿐이고, 글은 한 줄도 못 쓴다.

텍스트 쪽에서 LLM과 검색기가 별개 모델인 것과 정확히 같은 구조다. 검색기가 LLM을 대신할 수 없듯, [5]는 [2]를 대신할 수 없다.

파이프라인: 불량 이미지 → [5]가 유사 과거 사례 검색 → [2]가 현재+과거를 함께 놓고 판독 → [1] GLM-5.2가 종합 판단

16.3 "고성능이 꼭 필요한가" — 프레임을 바꿔서 답한다

"고성능이 필요하다"로 답하지 않는다. 그 프레임은 "좀 낮춰도 되지 않나"로 되돌아온다. 대신 두 가지로 답한다.

① 오판 1건의 비용. 불량을 놓쳐 유출되거나, 정상을 불량으로 잡아 라인을 세우면 그 1건의 손실이 자원 비용을 넘는다. 이 시스템의 성능은 편의가 아니라 오판율에 걸려 있다.

② 용도 차이. 범용 QA는 "그럴듯하면" 되지만, 품질 판정은 근거를 대고 감사에서 재현되어야 한다. 검증 가능한 판단과 범용 대화는 요구 수준이 다르다.

16.4 "사내 LLM API 쓰면 되지 않나" — 5가지 답

논거내용신청서 압축 문구
판단 정확도의 구조정확도 = ① 검색이 맞는 문서를 가져오나 + ② 모델이 우리 판정 논리를 아나 + ③ 근거를 우리 포맷으로 쓰나. API는 ③에만 관여하고, ①②는 가중치에 손댈 수 없으면 개선이 불가능하다.판단 정확도 개선 수단(검색기·모델 개인화)이 API에는 없음
검색기 파인튜닝 미제공임베딩·리랭커의 도메인 학습(hard negative 포함)은 LLM API 서비스 범위 밖이다. 검색이 틀리면 모델이 아무리 좋아도 오답이 나온다.RAG 검색기 도메인 학습은 자체 GPU에서만 가능
SFT·선호학습 불가판정 규칙을 프롬프트로 매번 주입하면 비용·지연이 커지고 규칙이 누락된다. SFT는 규칙을 가중치에 넣는다. 엔지니어 피드백 기반 선호학습(DPO)으로 쓸수록 좋아지는 구조는 가중치를 소유할 때만 성립한다.사용할수록 정확해지는 학습 루프는 자체 모델에서만 가능
에이전트 토큰 구조이상 1건당 도구 호출 5~15회 × 컨텍스트 누적. 종량 과금이면 건당 비용이 곱셈으로 늘고, rate limit이 동시 처리 건수의 상한이 된다. 그런데 이상은 몰려서 발생한다.라인 이상 동시다발 시 처리량 보장은 전용 자원에서만 가능
재현성·데이터 경계품질 판정은 감사 대응용 재현성이 필요하므로 모델 버전 고정이 필수다. 공용 API는 버전이 소리 없이 바뀐다. 불량 image·기준정보는 반출 통제 대상이다.판정 재현성(버전 고정)과 데이터 경계 확보

16.6 "VLM을 왜 두 개나 쓰나"

학습은 월 4회 돈다. 그때마다 대형 슬롯(GLM-5.2 12장 → 16장)이 학습으로 전환되는데, 그 시간 동안에도 불량 이미지는 계속 들어온다. 경량 Qwen3.6-35B-A3B가 상주하고 있어야 이미지 판독이 끊기지 않는다. 두 번째 VLM은 성능용이 아니라 무중단용이다.

16.7 "왜 대형 LLM 하나가 중심인가"

9절 워크플로우가 답이다. 모든 도구의 응답이 결국 텍스트가 되어 판단 LLM의 프롬프트로 들어간다. SQL 결과도, 이미지 판독문도, 검색된 문서도, 시계열 변화점도 전부 텍스트다. 그래서 GLM-5.2 하나가 전체를 지휘할 수 있고, 반대로 그 하나가 작으면 종합 판단이 무너진다.
