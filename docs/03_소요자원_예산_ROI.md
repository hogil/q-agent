## 1. GPU — 사내 수요등록 산출

### 1.1 등록 5건

| # | 등록 항목 | 학습 항목 | 입력 | 연산량 (E) | B300 (장) |
|---|---|---|---|---|---|
| 1 | GLM-5.2 판단·도메인·코딩 SFT | TOKEN / Text LLM | 743B · MoE · 1.5B tok · ep3 · 30일/dev2 | 10,031 | 4.89 |
| 2 | Qwen3.5-397B 멀티모달 SFT | TOKEN / Multimodal | 397B · MoE · 1.2B tok · ep3 · 30일/dev2 | 4,288 | 2.09 |
| 3 | Qwen3-Embedding·Reranker 튜닝 | TOKEN / Text LLM | 16B · 500M tok · ep5 · 15일/dev2 | 240 | 0.23 |
| 4 | GLM-5.2 Agent 정책학습 | STEP / GRPO eq=13 | 743B · step 70K · 15일/dev2 | 2,705 | 2.63 |
| 5 | Qwen3-VL-Embedding 튜닝 | TOKEN / Multimodal | 8B · 300M tok · ep15 · 15일/dev2 | 216 | 0.21 |
| | **합계** | | | **17,480** | **10.05** |

**H100 환산** — 스펙 계수 B300 : H100 : A100 = 1 : 2 : 4 이므로 10.05 × 2 = **20.1장** → **20장 신청**

### 1.2 산출 공식 (시스템 해독·재검증 완료)

```
TOKEN 연산량 = 모델크기 × 토큰수 × epoch × K계수          K: MoE 3 / dense 6
STEP  연산량 = 모델크기 × step수 × eq계수 × K_step        K_step = 4000, K계수 없음
B300 장수    = 연산량(E) ÷ (137 × 1회 dev 일수)
1회 dev 일수 = release 주기 ÷ dev 횟수
환산          H100 = B300 × 2,  A100 = B300 × 4          E = 10^18
eq 계수       rollout 1 / light 4 / PPO·GRPO 13 / RLHF 18 / heavy 25
```

공식을 코드로 다시 실행해 5건 전부 재현했다. 연산량은 5/5 일치하고, B300은 [1]번만 계산 4.88 대 화면 4.89로 0.01 차이가 나는데 화면 표시 반올림으로 본다. 어느 쪽이든 H100 환산은 20.1장으로 같아 신청 근거에 영향이 없다.

### 1.3 입력 시 주의 (같은 항목을 다시 등록할 때)

| 함정 | 결과 | 정상값 대비 |
|---|---|---|
| 모델크기 단위 오입력 (743B → 743M) | B300 0.0049 / H100 0.010장 | 1,000배 축소 |
| dense 모델인데 MoE 체크 | B300 4.88 (정상 9.76) | 절반으로 깎임 |
| dev 주기 30일 → 15일 | B300 9.76 / H100 19.5장 | 2배 증가 |

### 1.4 H100 20장 운용 배분

| # | 용도 | 장수 | 메모리 | 비고 |
|---|---|---|---|---|
| 1 | 판단 LLM 서빙 (TP) | 12 | 960GB | FP8 가중치 약 743GB — **적재 최소 10장**, KV 캐시·동시처리 여유 포함 12장 |
| 2 | 고정밀 VLM 서빙 | 5 | 400GB | 이미지 정밀 판독 |
| 3 | 경량 VLM·검색기 서빙 | 2 | 160GB | 상시 응답, 학습 중에도 유지 |
| 4 | 회귀평가 전용 | 1 | 80GB | 골든셋 회귀 게이트 |
| | **합계** | **20** | **1,600GB** | 남는 슬롯 0 |

**학습 모드** — 16장을 SFT·DPO로 전환하고 경량 서빙 4장을 유지해 이미지 기능이 끊기지 않는다 (월 4회).

> **★ 기존 GPU 제출본 정정 필요** — 서술형 '적합성' 필드에 `적재 8장`으로 적힌 부분이 있다. H100은 카드당 80GB이므로 743 ÷ 80 = 9.3, 즉 **적재 최소 10장**이 맞다. 8장(640GB)으로는 가중치가 물리적으로 올라가지 않는다. 이 8은 H200(141GB) 기준 초안이 남은 것이다. 서빙 12장·총 20장 결론은 바뀌지 않는다.

## 2. VM — BIG VM 5대 (Ubuntu 24.04 LTS)

### 2.1 구성

| Host | LB | 탑재 서비스 | vCPU | MEM | DISK |
|---|---|---|---|---|---|
| qagent-svc01 | O | Agent Runtime + Chat Gateway + 인메모리 캐시 | 64 | 1,024GB | 30,720GB |
| qagent-svc02 | O | Agent HA + 모니터링 + 회귀평가 하네스 | 64 | 1,024GB | 30,720GB |
| qagent-data01 | X | PostgreSQL 16 + pgvector (주) + ETL | 64 | 1,024GB | 30,720GB |
| qagent-data02 | X | PG standby(스트리밍 복제) + 백업 + 감사로그 | 64 | 1,024GB | 30,720GB |
| qagent-train01 | X | 데이터셋 빌드 + 모델 웨이트 병합 (시분할) | 64 | 1,024GB | 30,720GB |
| | | **합계 (웹 입력값)** | **320** | **5,120GB** | **153,600GB** |

### 2.2 대당 근거

| Host | CPU 근거 | MEM 근거 |
|---|---|---|
| svc01 | 세션 28 + 캐시 8 + Gateway 4 = 40 → 64 | 시계열 207 + 특징 300 + 사례 200 + 세션 ≈ 800GB |
| svc02 | Agent 28 + 모니터링 16 + 평가 16 = 60 → 64 | TSDB + 평가 + 캐시 복제 ≈ 716GB |
| data01 | 200 QPS 50 + ETL 11 = 61 → 64 | HNSW 300 + 핫캐시 400 + 버퍼 256 ≈ 1,020GB |
| data02 | 승격 시 primary 동일 부하 | 승격 시 956GB 동일 상주 |
| train01 | 5.0e6 core·s ÷ 22h = 63 → 64 | 웨이트 병합 900GB / 데이터셋 빌드 820GB |

**HA** — API는 svc01/02, DB는 data01/02 교차. 학습 병합을 train01 전담으로 분리해 GPU 슬롯을 회당 3~5시간 절약한다 (월 4회).

### 2.3 스토리지

| 항목 | 용량 | 근거 |
|---|---|---|
| NAS | 102,400GB (100TB) | 가중치 3세대 (743+1,486+497)GB×3 ≈ 8.2TB + 체크포인트 500GB×월4×3개월 = 6TB + 데이터셋 1.5TB×4세대 = 6TB + 캐시 3TB + 확산 증가·프리컴퓨트 |
| Object Storage | 51,200GB (50TB) | 이미지 2만장/일×2MB + Map 5만장/일×0.5MB = 65GB/일 × 600일 ≈ 39TB + 스냅샷·아카이브 10TB |
| 백업 | 153,600GB | VM DISK 1배 (일 단위) + WAL 아카이브 → NAS |

### 2.4 DB 데이터 용량

| 항목 | 용량 |
|---|---|
| 원문 | 200GB |
| 벡터 색인 | 300GB (halfvec 적용 시 여유 발생) |
| 키워드 색인 | 200GB |
| 판정 이력 (3년) | 274GB |
| 체크포인트 (90일) | 450GB |
| 시계열 요약 | 500GB |
| **소계** | **1,900GB** → 여유 포함 약 4TB (data01 로컬 30TB 內) |

관리형 DB 신청은 반려되어 data01/02 직접 설치로 확정했다. 오히려 스펙이 32코어·128GB에서 64코어·1,024GB로 올라가 인덱스 전량 상주가 가능해졌고, pgvector 버전을 자유롭게 고를 수 있어 실측한 0.8.1에서 halfvec을 쓴다 — 벡터 색인 크기가 절반이 된다.

## 4. 기대효과 산정

### 4.1 가정

| # | 가정 항목 | 값 | 근거 |
|---|---|---|---|
| 1 | 현행 판정 업무 시간 | 4시간 / 일·인 | 현업 실무 기준 (GPU 수요등록 제출 시 사용한 것과 동일) |
| 2 | 목표 판정 업무 시간 | 2시간 / 일·인 | 도구 조회·대조를 에이전트가 대신함으로써 절감 |
| 3 | 표준 근무 시간 | 8시간 / 일 | |
| 4 | 1인 연간 인건비 | 80,000,000원 | 사내 산정 기준값 |
| 5 | 적용 인원 | 1,000명 | 제조기술센터 품질·공정 엔지니어 |
| 6 | 연간 투자 | 347,794,165원 | 위 3장 |

### 4.2 산출

```
절감 업무 비율 = (4h / 8h) − (2h / 8h)            = 0.25  (25.0%)
연간 기대효과  = 0.25 × 80,000,000원 × 1,000명    = 20,000,000,000원  (연 200억)
연간 ROI       = 20,000,000,000 ÷ 347,794,165     = 57.5배
연간 회수 기간 = 365 ÷ 57.5                        = 6.3일
총투자 회수    = 695,588,330 ÷ 20,000,000,000 × 365 = 12.7일
```

### 4.3 연차별 효과 인식

| 구분 | 적용 범위 | 효과 인식 |
|---|---|---|
| 1차년 | 포토 1개 공정, 파일럿·무인 접수 | **전면 산정에 넣지 않는다.** 건당 처리 시간을 실측하는 구간으로 둔다 |
| 2차년 | 포토 + etch + CMP, 자동화 개시 | 실측치 기반으로 부분 인식, 확산 완료 시점부터 전면 적용 |
| 이후 | 1,000명 전면 적용 | 연 200억 (위 산정) |

1차년 효과를 산정에 넣지 않는 이유는, 넣으면 그 숫자를 근거로 심사를 통과한 뒤 실측치가 다를 때 설명할 방법이 없기 때문이다. 실측 구간으로 명시해 두는 편이 안전하다.

### 4.4 민감도 — 목표를 절반만 달성해도

| 목표 판정 시간 | 절감 비율 | 연간 기대효과 | 연간 ROI |
|---|---|---|---|
| **2.0시간 (본 지원서 기준)** | 25.0% | 200억 | **57.5배** |
| 2.5시간 | 18.8% | 150억 | 43.1배 |
| 3.0시간 | 12.5% | 100억 | 28.8배 |
| 3.5시간 | 6.3% | 50억 | 14.4배 |

하루 4시간에서 3.5시간, 즉 **30분만 줄어도 ROI 14배**다.

### 4.5 검증 방법

가동 후 다음을 실측해 분기 단위로 보고하고, 산정치와 차이가 나면 그때 조정한다.

| 지표 | 산출 |
|---|---|
| 건당 처리 시간 | 판단 시작 ~ 조치 확정 로그 |
| 골든 시나리오 정답률 | 회귀 러너 |
| 이벤트 처리 누락 | 접수 로그 대 감지 로그 대조 |

## 5. 확산 시 추가 자원

2차년 확산(etch·CMP)에 **추가 인프라를 요청하지 않는다.**

| 늘어나는 것 | 흡수 방법 |
|---|---|
| 조사규칙 문서 (공정별) | 문서이므로 자원 영향 없음 |
| 골든셋 (공정별) | 평가 데이터, 자원 영향 미미 |
| Inform Note 색인 | pgvector halfvec으로 색인 크기 절반 — 기존 300GB 산정에 여유 발생 |
| 이미지·Map 원본 | OBJ 50TB 산정에 600일치가 이미 반영됨 |
| 서빙 부하 | 동일 모델·동일 엔드포인트. 프롬프트 캐시 공유로 공정이 늘어도 모델은 늘지 않음 |

이것이 이 과제 구조의 핵심 이점이다. 공정을 늘릴 때 코어도 자원도 늘지 않는다. 5Q의 통과 조건에 **코어 변경 0**을 넣은 것이 이 주장의 검증 장치다.
