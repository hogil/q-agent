## 시스템 공식 (실측 해독 — 재사용 가능)
- TOKEN: 연산량 = 모델크기 × 토큰수 × epoch × K계수(MoE 3/dense 6)
- STEP: 연산량 = 모델크기 × step수 × eq × K_step(LLM Agent Standard=4000). K계수 없음
- B300 = 연산량(E) ÷ (137 × 1회 dev 일수). 1회 dev 일수 = release주기 ÷ dev횟수. H100 = B300×2, A100 = ×4
- eq: rollout=1 / light=4 / PPO·GRPO=13 / RLHF=18 / heavy=25
- 함정 3종: 단위 M/B 오입력(1,000배) · dense에 MoE 체크(절반) · dev 주기 짧을수록 장수 증가(같은 연산량을 짧은 기간에 끝내야 하므로)

## 방어 논거(유지)
- "고성능 필요" 프레임 금지 → 오판 1건의 비용(불량 유출/불필요 라인정지) + 용도 차이(검증 가능한 판단 vs 범용 QA)
- 사내 LLM API 대체불가: 검색기 파인튜닝 미제공 / SFT·DPO 불가(쓸수록 좋아지는 루프는 가중치 소유 시만) / rate limit=동시 처리 상한 / 재현성(버전 고정)·데이터 경계
- 사내 공용 RAG 대체불가: 도구 호출형 검색 미지원, 용어 병기·ID 보호·형태소 색인·메타 필터·recall 지표 통제 불가
- 2-VLM 근거: 학습 기간(월 4회) 대형 슬롯 전환 시 이미지 무중단은 경량 상주가 보장

표기 원칙: **서비스 대상 = 제조기술센터 품질·공정 엔지니어 약 1,000명** — 전 서류 동일 (소규모 단계·특정 그룹 표기 사용 금지. ROI 산정 인원과 일치 필수).

## Application 명 / 정의
- **Application 명 (후보)**: 품질 이상감지·판단 AI Agent (Q-Agent)
- **정의 (1문장형)**: 제조 품질 데이터(Trend·Map·Image)와 사내 지식을 AI Agent가 상시 감시·자율 분석하여, 근거가 인용된 불량 판단과 조치안(Release/Hold)을 제시하고 엔지니어 피드백으로 지속 정확해지는 LLM 기반 품질 판단 자동화 시스템.
- **정의 (2문장형)**: 제조 품질 데이터(Trend·Map·Image)와 사내 지식(GPM·작업 Note)을 AI Agent가 24시간 감시하고, 이상 감지 시 필요한 시스템을 스스로 조회·분석하여 근거가 인용된 판단과 조치안(Release/Hold)을 제시하는 품질 판단 자동화 시스템. 엔지니어의 검증·피드백이 학습으로 반영되어 사용할수록 판단이 정확해짐.

## 섹션 분업 원칙
| 섹션 | 담당 | 여기만 나오는 것 |
|---|---|---|
| Application 정의 | 한 줄 요약 | 시스템 정체성 압축 |
| Application 설명 | 업무가 뭔가, 왜 필요, 업무 흐름 | 감시 공백, 노하우 자산화, HITL |
| 모델 준비 단계 | 모델 선정·학습 계획 | 모델명, 학습 3단계, 골든셋, 월 4회 |
| GPU 사용 적합성 | 왜 GPU 필요 | 743GB 산술, 도구 호출 5~15회, 반출 불가·온프레 |
| GPU 자원 효율성 | 어떻게 아껴 쓰나 | MoE/FP8/캐시, 시분할, 리포팅 |
| 수요등록표 | 학습량 숫자 | 토큰·step·epoch |

Application 설명에는 GPU 장수·모델명·학습 기법 약어·수치를 넣지 않는다.

## 역할/목적
품질 이상 1건의 판단에는 Trend 조회, Map·Image 확인, GPM 기준 대조, 과거 이력 검색 등 여러 시스템을 오가는 수작업 분석이 필요하며, 판단 품질이 담당자 경험에 좌우됨. 본 시스템은 이 분석 과정을 AI Agent가 대행함 — 계측 Trend를 24시간 감시해 이상을 조기 포착하고, 판단에 필요한 시스템을 스스로 조회·분석하여 근거가 인용된 판단과 조치안(Release/Hold)을 제시하며, 엔지니어는 대화(Chat)로 언제든 분석을 지시·검증함. 판단 소요 시간 단축(1인당 일 4시간 → 2시간), 야간·휴일 감시 공백 제거, 판정 일관성 확보를 달성함.

## 주요 기능
- 계측 Trend 24시간 자동 감시 — 변화 시점·변화량을 특정한 조기 경보
- 이상 발생 시 판단 정보 자동 수집: GPM 기준정보 조회, Wafer Map·Defect Image 판독, 유사 과거 사례 검색(문서+이미지), 변경점 이력 대조
- 진성 불량 판단 및 Release/Hold 조치안 생성 — 판단 근거 원문 인용
- 대화형 분석(Chat): 자연어 질의에 실데이터 기반 답변
- 판정·조치 전 과정 자동 기록 — 감사·재발 분석 대응

## 시스템 특성
- 판단 LLM, 이미지 판독 모델, 불량 분류 모델, 시계열 이상탐지 모델, 검색 모델을 각각 사내 데이터로 개별 학습하여 운영하는 자체 모델 스택
- LLM이 SQL·이미지·시계열·검색 도구를 사안에 따라 자율 선택·호출하고 결과를 종합하는 오케스트레이션 구조
- 사내 용어 사전 기반 하이브리드 검색(키워드+의미+이미지 유사도)으로 informnote·과거 사례 정확 검색
- Agent의 시스템 접근은 조회 전용으로 제한, 조치는 엔지니어 승인 후 실행하는 Human-in-the-loop 통제 구조

## 신규 구축 필요성
첫째, 감시 공백 — 이상은 야간·휴일을 가리지 않으나 수작업 분석은 근무 시간에 묶여 조기 대응 기회를 놓침. 둘째, 판정 노하우의 유실 — 베테랑의 판단 기준이 개인 경험에 머물러 인력 이동 시 조직에서 사라짐. 본 시스템은 판정 이력과 피드백을 학습 데이터로 축적해 조직 자산화함. 셋째, 기존 수단의 한계 — 사내 공용 LLM API·공용 RAG는 문서 질의응답 전용으로, DB 조회·이미지 판독·Trend 분석을 결합한 도구 호출형 분석과 사내 용어·판정 논리의 도메인 학습이 불가하여 자체 구축 필요.

## 비즈니스 프로세스
1. (상시) Trend·Map·Image 수집 → 시계열 모델이 변화점 검출 시 Agent 자동 기동 / (수시) 엔지니어 Chat 질의로도 동일 분석 기동
2. Agent가 GPM 기준·변경점 이력 조회, 이미지 판독, 유사 사례 검색을 자율 수행·종합
3. 진성 여부 판단 → Release/Hold 조치안을 근거와 함께 제시 → 엔지니어 승인/수정
4. 처리 결과·피드백이 학습 데이터로 자동 축적 → 정기 재학습·검증 절차를 거쳐 반영 — 사용할수록 정확해지는 순환

## 지원 대상/제품/공정
- **지원 대상: 메모리사업부 제조기술센터 품질·공정 엔지니어 약 1,000명**
- 사용 부서/조직: ◇ (사내 조직명 기입)
- 지원 공정: FAB 전 공정, EDS 전 공정
- 지원 제품: 메모리 전 제품군 (DRAM, NAND 등)
- 처리 데이터: 설비 FDC Sensor, Metrology Trend, Wafer Map, Defect Image, GPM 기준정보, 엔지니어 작업 Note(Interlock 이력), 도면·리포트 문서, 판정·조치 이력, 사내 용어 사전

## Application 기능/역할 (4분류)
1. **상시 감시·조기 경보** — 시계열 모델+변화점 검출로 "언제부터, 얼마나"를 수치로 특정. 완만한 shift·미세 변동 24시간 포착
2. **도구 호출 종합 분석** — 판단 LLM이 필요한 정보를 스스로 결정해 수집(GPM·변경점 조회, Map·Image 판독, 유사 사례 검색, 도면 판독) 후 원인 가설 수립·검증
3. **근거 기반 판단·조치** — 진성 판단 + Release/Hold 조치안 + 근거 원문 인용 + 전 과정 자동 기록. 조치 실행은 엔지니어 승인 통제
4. **전 모델 자체 학습 체계** — 판단 LLM·이미지·검색 모델을 각각 사내 데이터로 개별 학습. 피드백(채택/수정/기각) 자동 축적 → 정기 반영, 검증 통과 버전만 배포

- 관리형 DBaaS(dbqie, 등급 C 32c/128GB/4TB, 월 748,153원) 신청 → **실패**
- **확정: BIG VM data01/data02에 PostgreSQL+pgvector 직접 설치** — VM 신청서 v10~v13의 원래 설계로 회귀. 서류 정합 유지(data01/02 산정근거에 이미 명시됨)
- 실패 사유 확인 필요: 자원/절차 문제면 VM 설치 진행, "관리형만 허용" 정책 사유면 재검토

## 직접 운영의 이점
- 스펙 상향: 관리형 32c/128GB → data01 64c/1TB (벡터 인덱스 전량 메모리 상주 가능 — 관리형에선 불가)
- pgvector 버전 자유 선택 (0.7+ halfvec로 색인 절반)
- shared_buffers 등 튜닝 자유, 월 748,153원 절감

## 직접 운영 체크리스트
1. **HA**: data01(primary)→data02(standby) 스트리밍 복제 + 승격 절차. 자동 failover 필요 시 Patroni (초기 수동 승격 가능)
2. **백업**: pgBackRest/pg_basebackup — 일 풀백업은 VM DISK 백업(신청분), WAL 아카이브는 NAS. 복구 리허설 분기 1회
3. **패치**: 마이너 업데이트 직접 — 버전 고정(판정 재현성) 원칙과 충돌 없게 월 4회 학습 주기 창에서만 적용
4. **모니터링**: svc02 Prometheus에 postgres_exporter 추가
5. **보안**: 사내 DB 정책 준수(계정 분리·접근 통제), 감사로그는 data02 설계에 포함

## 데이터·용량 설계 (유지 — dbqie 산정 수식 그대로 data01/02에 적용)
- 저장 구성: 원문 200GB + 벡터 색인 300GB(청크 5,000만×2KB+HNSW×3) + 키워드 색인 200GB + 판정 이력 274GB(일 5,000건×50KB×3년) + 체크포인트 450GB(일 1,000세션×5MB×90일) + 시계열 요약 500GB = 1,900GB + WAL·재색인 여유 = ~4TB (data01 30TB 로컬 디스크 內 여유 충분)
- 기준: 1,000명·전 공정 확산, 이력 3년 보존
- 아키텍처: WRITERS(ETL·판정기록·체크포인트·시계열 배치) → data01 → READERS(Agent 하이브리드 검색·캐시 웜업·학습 추출·감사). 구성도는 dbarch.png의 dbqie를 data01로 치환해 사용

## (보관) 관리형 신청 시 사용했던 산출근거 — 재신청 대비
- vCPU 32: 검색 피크 100QPS×0.25core·s=25 + WAL·재색인 병행 → 32
- MEM 128: 버퍼 32+핫캐시 60+커넥션 = ~120 → 128
- DISK 4,000: 데이터 1,900GB × 여유 2배 = 3,900 → 4,000
- 활용안/솔루션 4필드·상세 표 1행·웹 산출근거 문안은 세션 대화 원문 참조
