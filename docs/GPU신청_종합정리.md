## 2. 등록 5건과 산출 공식 (원본: `설계/GPU신청_수요등록표.md`)

| # | 등록 항목 | 학습항목 | 입력 | 화면 연산량(E) | 산출 B300 |
|---|---|---|---|---|---|
| 1 | GLM-5.2 판단·도메인·코딩 SFT | TOKEN / Text LLM | 743B · MoE체크 · 1.5B tok · ep3 · 30일/dev2 | 10,031 | 4.89 |
| 2 | Qwen3.5-397B 멀티모달 SFT | TOKEN / Multimodal | 397B · MoE체크 · 1.2B tok · ep3 · 30일/dev2 | 4,288 | 2.09 |
| 3 | Qwen3-Embedding-8B + Reranker-8B 검색기 튜닝 | TOKEN / Text LLM | 16B · MoE해제 · 500M tok · ep5 · 15일/dev2 | 240 | 0.23 |
| 4 | GLM-5.2 Agent 정책학습 (GRPO) | STEP / LLM Agent Standard | 743B(단위 B!) · step 70,000 · eq13 · 15일/dev2 | 2,705 | 2.63 |
| 5 | Qwen3-VL-Embedding 멀티모달 검색기 튜닝 | TOKEN / Multimodal | 8B · MoE해제 · 300M tok · ep15 · 15일/dev2 | 216 | 0.21 |
| | **합계** | | | **17,480** | **10.05** |

**환산: B300 10.05 → H100 20.1장 / A100 40.2장**

### 시스템 공식 (실측 해독 — 재사용 가능)

```
TOKEN   연산량 = 모델크기 x 토큰수 x epoch x K계수(MoE 3 / dense 6)
STEP    연산량 = 모델크기 x step수 x eq x K_step(LLM Agent Standard 4000). K계수 없음
B300    = 연산량(E) / (137 x 1회 dev 일수),  1회 dev 일수 = release주기 / dev횟수
환산     H100 = B300 x 2,  A100 = B300 x 4,  E = 10^18
eq계수   rollout 1 / light 4 / PPO·GRPO 13 / RLHF 18 / heavy 25
```

미등록과 사유(심사 대응): Qwen3.6-35B(SFT 없이 기본 서빙) / ConvNeXt·PatchCore·PatchTST(sample 기반 소형, 시스템 산출 ~0) / CUSUM·BOCPD(통계) / PaddleOCR(0.9B, 산출 ~0)
→ 답변 한 문장: "sample 기반 소형 모델로 등록 시스템 산출이 0에 수렴하며, 학습·서빙 모두 기존 등록분 여유 내에서 처리됩니다."

## 3. ★ 신규 — 공식 역검증 결과

공식을 코드로 다시 돌려 문서값과 대조했다. 재신청 때 이 공식을 그대로 쓸 수 있다는 뜻이다.

| # | 계산 연산량 | 문서값 | 판정 | 계산 B300 | 문서 B300 | 판정 |
|---|---|---|---|---|---|---|
| 1 | 10,031 | 10,031 | 일치 | 4.88 | 4.89 | **0.01 차** |
| 2 | 4,288 | 4,288 | 일치 | 2.09 | 2.09 | 일치 |
| 3 | 240 | 240 | 일치 | 0.23 | 0.23 | 일치 |
| 4 | 2,705 | 2,705 | 일치 | 2.63 | 2.63 | 일치 |
| 5 | 216 | 216 | 일치 | 0.21 | 0.21 | 일치 |
| | | | | **10.04** | **10.05** | |

**연산량은 5건 전부 정확히 재현된다.** B300은 4건 일치, [1]만 0.01 차이가 난다.
137이 아닌 다른 상수(136.6~136.9)를 쓰면 [1]은 맞지만 [4]가 2.64로 어긋난다 — 하나의 상수로 둘 다 맞출 수 없다. 화면 표시 단계의 반올림 차로 본다.
**어느 쪽으로 계산해도 H100 환산은 20.1장으로 같다. 신청 근거는 흔들리지 않는다.**

### 입력 함정 3종 (항목 [1] 기준 실계산)

| 함정 | 정상 | 틀렸을 때 | 영향 |
|---|---|---|---|
| ① 모델크기를 743M으로 (단위 오입력) | B300 4.88 / H100 9.8장 | B300 0.0049 / H100 0.010장 | **1,000배 축소** — "GPU가 필요 없다"가 된다 |
| ② dense 모델에 MoE 체크 | B300 9.76 (dense K=6) | B300 4.88 | **절반으로 깎임** — 8B/16B 검색기는 dense다 |
| ③ dev 주기 30일 → 15일 | B300 4.88 / H100 9.8장 | B300 9.76 / H100 19.5장 | **2배 증가** — 직관과 반대다 |

입력 전 확인 3줄: ① 모델크기 칸의 단위가 B인지 눈으로 본다 (특히 STEP형 [4]) ② MoE 체크박스가 그 모델의 실제 구조와 맞는지 본다 ③ release 주기·dev 횟수를 등록 기준(30일/dev2, 15일/dev2)과 맞춘다.

## 4. ★ 신규 — 제출본 오류 1건 발견: "적재 8장"

서술형 '적합성' 필드에 이렇게 적혀 있다:

> FP8 가중치 ~743GB(**적재 8장**/서빙 12장/학습 16장+)

**H100은 카드당 80GB다. 743 ÷ 80 = 9.3 → 최소 10장이어야 가중치가 올라간다. 8장 = 640GB로는 물리적으로 안 올라간다.**
이 "8"은 H200(141GB) 기준으로 쓴 예전 초안의 숫자가 그대로 남은 것이다.

**고쳐 쓸 문구**

> FP8 가중치 ~743GB(**적재 최소 10장** / 서빙 12장 / 학습 16장+)

결론(서빙 12장, 총 20장)은 바뀌지 않는다. 이 한 줄만 고치면 된다. 다만 심사자가 743÷80을 직접 계산하면 바로 드러나는 자리다.

## 7. ★ 폐기본 경고 — `GPU수요신청_등록표.xlsx` (2026-07-28 21:26판)

로컬에 남아 있는 이 엑셀은 **H200 20장 / 8건 등록 / B300 환산 12.5**를 목표로 하던 **중간 초안**이다. 최종 제출 상태와 다르다.
게다가 **존재하지 않는 모델명**과 낡은 값이 들어 있다:

- `Qwen3.5-VL` — **이런 모델은 없다.** 멀티모달은 Qwen3.5-397B-A17B / Qwen3.6-35B-A3B / Qwen3-VL-Embedding이다.
- `bge-m3` — 검색기는 **Qwen3-Embedding-8B + Qwen3-Reranker-8B**로 교체됐다.
- `753B MoE·활성 40B` — GLM-5.2는 **743B-A39B**다. 744B도 753B도 아니다.
- `H200 141GB × 20 = 2,820GB` 메모리 계산과 8/8/4 배분 — **여기가 "적재 8장" 오류의 출처**다.

**조치:** H100 20장 / 5건 최종본 + 역검증 시트로 **`GPU수요신청_최종본_H100_20장.xlsx`를 새로 만들었다.** 옛 파일은 참고용으로만 두고 제출·인용에 쓰지 않는다.

## 8. 남은 확인 사항 5 + 1건

| # | 확인 사항 | 상태 | 내용 |
|---|---|---|---|

| ② | Grafana·Loki 사내 미러 등록 | 확인 중 | 미등록이면 반입 절차 별도 필요 |

## 9. 표기 규칙 — 전 서류 공통

| 규칙 | 이유 |
|---|---|
| 대상은 항상 **"제조기술센터 품질·공정 엔지니어 약 1,000명"** | 소규모 단계·특정 그룹 표기를 쓰면 ROI 산정 인원과 어긋난다. 기대효과 200억이 통째로 흔들린다 |
| 모델현황 **표 비고에 등록번호 태그를 넣지 않는다** | 등록번호는 시스템이 부여하는 값이라 문서에 박으면 곧 어긋난다 |
| Application 설명에 **GPU 장수·모델명·학습 약어·수치 금지** | 섹션 분업 원칙. 칸마다 담당이 다르다 |
| **지어낸 퍼센트는 쓰지 않는다** | 골든셋 실측 전까지 능력 누적표의 "답변의 질" 줄은 비워 둔다 |
| 미기입 칸은 **◇** 하나로만 표시 | 기호를 섞으면 무엇이 남았는지 셀 수 없다 |
