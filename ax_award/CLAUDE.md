# CLAUDE.md — 사내 AX 경진대회 지원서 (.docx) 작업 규칙

이 폴더(`ax_award/`)의 유일한 목적: **사내 AX Award 지원서 Word 문서(.docx) 1건 산출.**

대상 과제는 **반도체 품질 이상감지·판단 AI Agent Orchestration 구축(Q-Agent)** — 2개년 단계 과제다.
이 작업은 새로 쓰는 것이 아니라, 이미 완성된 **정본 `docs/01_과제지원서_본문.md` 를 AX Award 양식
5장으로 압축**하는 것이다. 사실관계 출처와 우선순위는 §8, 실제로 넣을 값은 §9 사실 카드에 있다.

## 0. 절대 규칙 (위반 금지)

1. **서식 규격(§3·§4)은 임의 변경 금지.** 여백·글꼴·글자크기·표 너비·열 너비·행 높이는
   사용자가 지정한 값이 유일한 정답이다. "보기 좋게" 바꾸지 않는다.
   규격대로 하면 깨지는 곳이 있으면 → **고치지 말고 §7에 적고 사용자에게 묻는다.**
2. **`IIII. 경영효과` 의 로마숫자 표기를 `IV` 로 고치지 않는다.** 사내 양식 원문 그대로다.
   `I. 개요` / `II. Process` / `III. Tech` / `IIII. 경영효과` — 이 4개가 확정 표기.
3. **없는 실적·수치를 지어내지 않는다.**
   - **쓸 수 있는 실측치는 아래 목록이 전부다.** 여기 없는 수치는 만들지 않는다.

     | 지표 | 값 | 출처 · 반드시 붙일 단서 |
     |---|---|---|
     | 검색 recall@10 | **0.500** | Q-Agent 회귀 러너 실측. `골든 4건 / 색인 50건` 을 같이 쓴다 |
     | 검색 hit@1 | **1.000** | 선행 프로토타입 B `eval/eval_retrieval.py`, 26질의 / 코퍼스 4,427청크 |
     | 검색 hit@1 (하드셋) | **0.957** | 위 레포 `eval/eval_hard.py`, 본문 세부·패러프레이즈·교차언어·distractor 38질의 |
     | 검색 hit@1 (확장 후) | **0.962** · 지연 **1.29초** | 코퍼스 60→4,427청크 2.4배 확장 뒤에도 유지 |
     | 색인 규모 | **5,291청크 / 103문서** | 위 레포, PostgreSQL 16 + pgvector |
     | 임베딩 군집 AMI | **0.956** | 선행 프로토타입 A(`D:\project\failure_agent`) `docs/ARCHITECTURE.md` |
     | 임베딩 군집 ARI | **0.860** | 위와 동일 |
     | 노이즈 비율 | **0.52%** | 위와 동일 |
     | 학습 데이터 | **43개 불량 class · class 당 30장 · 총 900 wafer** | 위와 동일 |

   - **AMI·ARI 를 "판정 정확도"로 바꿔 부르지 마라.** 군집 품질이지 진단 정답률이 아니다.
     반드시 "선행 프로토타입에서 학습한 불량 이미지 임베딩의 군집 지표" 로 명시한다.
   - **hit@1 과 recall@10 = 0.500 을 섞지 마라.** 서로 다른 시스템·다른 코퍼스의 값이다.
     hit@1 은 선행 프로토타입 코퍼스, 0.500 은 Q-Agent 골든셋(4건/50건)이다. 한 문장에 나란히 놓지 않는다.
   - **프로토타입이 쓴 모델을 본 과제 모델로 바꿔 쓰지 마라.** 프로토타입 실측은 bge-m3 + bge-reranker-v2-m3
     기준이고, 본 과제는 Qwen3-Embedding-8B + Qwen3-Reranker-8B 로 교체 예정이다.
     "Qwen3 로 hit@1 0.957 을 냈다" 는 거짓이 된다. 외부 상용 LLM 이름도 지원서에 쓰지 않는다.
   - 판정 정답률·환각 차단율·시간 단축률에는 **어떤 퍼센트도 새로 만들어 쓰지 않는다.**
     정본 문서가 "목표 정답률에 임의의 퍼센트를 쓰지 않는다"를 명시 원칙으로 못 박았다 — 그대로 승계한다.
   - 기대효과 200억·ROI 57.5배는 **산출식이 있는 값**이므로 쓴다(§9-5). 산출식과 함께 쓴다.
   - **1차년 효과는 전면 산정에 넣지 않는다.** 포토 1개 공정 실측 구간이다. 200억은 3개 공정 확산 후
     1,000명 전면 적용 전제값이며, 이 전제를 반드시 문장에 붙인다.
4-A. **`I. 개요 > 분류` 의 두 칸은 더미로 확정이다. 건드리지 마라.** (사용자 지시 2026-08-08)
   - 대상 : `적용시점`(V_WHEN) · `횡전개 범위`(V_SPREAD)
   - **수정 금지** — 문구를 다듬거나 줄이거나 근거를 붙이지 않는다.
   - **채점 제외** — 심사·디자인·계획·마스터 어느 단계에서도 이 두 칸을 평가하거나 감점 사유로 삼지 않는다.
     "적용시점에 근거가 없다", "횡전개 범위가 모호하다" 같은 지적은 애초에 내지 않는다.
   - 분량 계산에는 그대로 포함한다(지면은 차지하므로).

4. **모르는 값은 사용자에게 묻지 않는다. 그냥 더미값을 채워 넣고 진행한다.**
   (사용자 지시 2026-08-07 — 이 지원서뿐 아니라 평가·다른 산출물에도 동일 적용되는 절대규칙)
   - 조직명·인명·부문명·일자처럼 사람이 정해야 하는 칸은 그럴듯한 더미값으로 채운다.
     빈칸·`◇`·`【확인필요】` 로 남겨 두고 물어보지 않는다.
   - **채운 더미값은 작업 보고 때 목록으로 한 번에 제시**해 사용자가 통째로 바꿔 넣을 수 있게 한다.
     문서 본문에는 표시 기호를 남기지 않는다.
   - 예외는 §0-3 의 성능 수치뿐이다. 정답률·환각차단율 같은 **성능 퍼센트는 더미로도 만들지 않는다**
     (정본이 명시 금지한 항목이라 더미가 곧 허위 실적이 된다). 실측 `recall@10 = 0.500` 만 쓴다.
   - 현재 더미값: 지원부문 `제조 AX 부문` / 팀·그룹 `제조기술센터 품질기술그룹` / 대표자 `홍길동`
5. **리소스 얘기를 하지 않는다.** (사용자 지시 2026-08-07, 절대규칙 / 프로젝트 원칙 —
   `docs/GPU신청_Application설명.md` §섹션 분업 원칙 "GPU 장수·수치를 넣지 않는다")
   자원은 **별건(GPU 수요등록·VM 신청)** 이다. 이 지원서에는 **아래 채점 항목에 해당하는 것만** 쓴다.
   - **금지** : GPU 장수·서빙 배분 · VM 대수/코어/메모리 · NAS·OBJ 용량 · FP8·80GB·743GB 같은
     하드웨어 수치 · DB 서버 버전 · 소요 인력 표 · 자원 산출근거 · "인프라" 라는 단어 자체
   - **허용** : 알고리즘·모델명과 그 **선택 근거**(TECH 30점이 요구) · 투자 금액과 ROI
     (경영효과 산출식의 성분) · **"공정이 늘어도 추가 자원을 요청하지 않는다"** 는 확산 비용 논지
     (수치 없이 이 문장만)
6. **산출물·중간 결과 삭제 금지.** `out/` 아래 파일과 렌더 이미지는 사용자 명시 요청 없이 지우지 않는다.
   수정은 **새 버전 파일명**으로 만든다(`_v1` → `_v2` → …). 같은 파일 덮어쓰기 금지.
6. **눈으로 확인하기 전에 "완성"이라고 말하지 않는다.** §6 검증 절차(PDF 렌더 → 이미지 → 육안 확인)를
   통과하지 않은 파일은 미완성이다. 페이지 수·행 높이·글자 잘림을 실제 렌더로 확인한다.
7. **채점 기준(§2)에 배점이 없는 내용은 쓰지 않는다.** 지면이 고정(5장)이므로 배점 없는 서술은
   배점 있는 서술의 자리를 뺏는 손해다.
8. **AI 말투 금지 — 사람이 쓴 글로 읽혀야 한다.** (사용자 지시 2026-08-07, 절대규칙)
   정본은 이미 사람이 쓴 좋은 한국어다. **문장을 새로 지어내지 말고 정본 문장을 가져와 어절만 덜어낸다.**
   **문체 검수는 최소 3회 반복한다.** 1차는 문장만 읽으며 어색한 어순·명사 나열·번역투를 고치고,
   2차는 페이지 안에서 앞뒤 문장이 자연스럽게 이어지는지 확인하며, 3차는 최종 렌더를 소리 내어 읽는
   기준으로 다시 고친다. 세 번 중 한 번이라도 어색하면 완료로 처리하지 않는다.
   **최우선 금지어는 다음 10개다: `완전한 / 살아있는 / 스스로 / 통째로 / 정거장 / 자란다 / 닫힌다 /
   관문 / 걷는다 / 돌파`. 제목·도식·본문 모두 예외가 없다.** 입력·처리·반환·검증·승인처럼 실제 동작을
   나타내는 말로 바꾼다. `답이 자란다`, `실물에 닿는다`, `끝이 다음 시작을 키운다`처럼 뜻보다 수사가
   먼저 보이는 표현도 쓰지 않는다. (사용자 지시 2026-08-11 — 이전 확정 제목 문구보다 우선)
   매 버전 렌더 확인 때 아래를 함께 점검하고, 걸리면 고친 뒤 다음 버전으로 넘어간다.
   - 한 문장에 `~하고, ~하며, ~한다` 를 겹쳐 쌓지 않는다. 끊어서 두 문장으로 쓴다.
   - 항목마다 같은 문형을 반복하지 않는다 (`…를 통해 …를 확보한다` 가 줄줄이 이어지면 AI 티가 난다).
   - `즉` `따라서` `또한` `아울러` 같은 접속 부사를 문단마다 붙이지 않는다.
   - 결론을 다시 요약하는 마무리 문장을 습관적으로 달지 않는다.
   - 형용사로 부풀리지 않는다(`혁신적인` `획기적인` `강력한`). 사실과 수치가 대신하게 둔다.
   - 능동태·단정형으로 짧게. 정본의 `…판단하지 않는다` `…자리가 구조적으로 없다` 같은 어조를 따른다.
   - **명사 나열로 제목을 만들지 않는다.** `데이터 자산 임계 도달` `공개 모델 성숙` `검증 체계 완비`
     처럼 서술어를 지운 명사구는 보고서 티가 아니라 AI 티다. `데이터가 쌓였다` 처럼 문장으로 쓴다.
   - **번역투 마무리를 달지 않는다.** `이것이 …의 전형이다` `…를 의미한다` `…라 할 수 있다`.
   - **비유를 함부로 쓰지 않는다.** `다섯 정거장` `함정을 밟는다` 처럼 원문에 없던 비유는 튄다.
   - **용어를 지어내지 않는다.** contrastive 는 `대조 학습`이다. `대비학습` 같은 조어를 만들지 마라.
   - **한 번 고치고 끝내지 않는다.** 말투 점검은 **버전마다 다시 돌린다.** 소스(디자인 export)가
     새로 오면 문구가 되살아나므로, 교정은 `ax_award/html/patches.py` 의 TONE 목록으로 유지해
     빌드할 때마다 자동 적용되게 한다. 새로 발견한 표현은 그 목록에 계속 더한다.
9. **충돌하면 사용자 지시 > 이 CLAUDE.md > 정본 순이다.**
   정본에 없다는 이유로 사용자가 직접 지시한 내용(제목 문구, agentic RAG·Image/Trend Agent 구성,
   자동조치까지 간다는 서술, 선행 프로토타입 실측치)을 지우거나 되돌리지 마라.
10. **정본은 `docs/01_과제지원서_본문.md` 다.** 이 지원서는 그 내용을 AX Award 양식 5장으로 **압축**하는
   작업이지, 새로 쓰는 작업이 아니다. 정본에 없는 주장·수치·일정을 만들어내지 않는다.
   정본과 충돌하는 옛 서술(단년 과제, 회수 6.4일 등)은 정본을 따른다.

- Process 60점이 최대 비중이다. **"E2E 전체 프로세스를 대체"** 를 그림과 문장으로 못 박아야 한다.
  단일 기능 개선으로 읽히면 20점이 통째로 날아간다.
- TECH 30점은 **"왜 AI/Agent여야 하는가"(= 룰/기존 자동화로 안 되는 이유)** 와
  **"왜 이 알고리즘인가"** 두 축이다. 모델 자랑이 아니라 *선택 근거*를 쓴다.
- TECH 서술 4요소(양식 지시): ① AI/Agent 당위성 ② 알고리즘 선택 근거 ③ 성능 지표 ④ 개선 수행 과정.
  네 개 다 있어야 한다. 하나라도 빠지면 감점.
  ③ 성능 지표 칸의 실측치는 **recall@10 = 0.500 하나뿐**이다(§0-3). 나머지는 *측정 체계·회귀 게이트가
  이미 서 있다*로 쓴다 — 검증기 5칙과 회귀 러너가 곧 성능 관리 체계라는 논지가 이 칸의 방어선이다.
- **BIZ 10점 방어의 핵심은 §10 선행 추진 실적이다.** "신규과제라 성과 없음"이 아니라
  설계 31종·스켈레톤 실행·회귀 러너·recall 실측·DB 구축·GPU 수요등록 완료까지 이미 서 있다.
  이걸 빼면 10점 중 상당수를 버린다.

### 5-2. 반드시 알아야 할 함정
1. **한글 글꼴은 eastAsia 를 지정해야 적용된다.**
   python-docx 의 `run.font.name = "바탕체"` 는 `w:ascii`/`w:hAnsi` 만 쓴다. 한글은 East Asian 문자로
   분류돼 테마 글꼴로 렌더된다. 반드시 아래처럼 `w:eastAsia` 를 직접 넣는다.
   ```python
   from docx.oxml.ns import qn
   run.font.name = "바탕체"
   run._element.rPr.rFonts.set(qn("w:eastAsia"), "바탕체")
   ```
   (docx-js 를 쓰지 않는 이유가 이것 — eastAsia 지정이 안 돼 XML 후처리가 필요하다.)
2. **표 열 너비는 표·셀 양쪽에 설정.** `table.autofit = False`, `table.columns[i].width` 와
   `cell.width` 를 모두 지정한다. 병합 셀은 병합 후 다시 너비를 넣는다.
3. **행 높이는 `WD_ROW_HEIGHT_RULE.AT_LEAST`.** §3-4 참조.
4. **페이지 나눔은 문단 단위로만 가능하다.** 표 한복판에서 페이지를 끊으려면 해당 행이 시작되는
   셀 안 첫 문단에 `page_break_before` 를 주거나, 페이지별로 표를 분리한다.
   → 이 문서는 **페이지마다 표를 따로 만들고 사이에 페이지 나눔**을 넣는 방식이 안전하다.
5. **`\n` 금지.** 줄바꿈은 문단을 나누거나 `run.add_break()` 를 쓴다.

### 9-0. 시스템 정체성 — 이 한 문장이 문서 전체의 축이다 (사용자 지시 2026-08-07)
**완전한 품질 AI Agent Orchestration — 감지부터 자동조치까지.**
supervisor 형 마스터 Agent 가 하위 전문 Agent 와 사내 시스템 도구를 스스로 골라 호출하고,
근거를 인용한 판단과 조치를 내며, 승인 이력이 쌓인 시나리오는 **자동조치까지 연다.**

| 구성원 | 하는 일 |
|---|---|
| 마스터 Agent (supervisor) | 증상 분류 → 조사 설계 → 하위 Agent·도구 자율 호출 → 증거 종합 → 판단·조치 |
| **Trend Agent** | 계측·FDC 시계열 상시 감시. 변화 시점·변화량을 수치로 특정해 조사를 자동 기동 |
| **Image Agent** | wafer map 공간 패턴 분류, defect image 유형 판독. 이미지 저장소에서 **임베딩 유사도**로 닮은 과거 불량 이미지를 찾고, 거기 붙은 **메타데이터·파일 경로를 키로 삼아** 그 사고의 원인·조치 이력을 RDB 에서 정확히 끌어온다 — **유사도로 좁히고 키로 확정한다** |
| **Agentic RAG** | 엔지니어 Inform 이력 검색 + 사내 지식 저장 검색이 여기 묶인다. 질의 재작성 → 하이브리드 검색(벡터+BM25+메타) → 리랭크 → 근거 선별, 부족하면 스스로 재검색. **문서만이 아니라 과거 사고 리스트·원인·조치 메타데이터가 든 RDB 도 함께 조회**해 정형·비정형을 한 근거팩으로 묶는다 |
| **사내 시스템 Tool Calling** | SPC·MES·YMS·EES·QMS 를 조회 전용으로 호출. 통계·공통성 분석은 코드가 계산 |

입력은 **두 갈래로만 시작한다** — ① 엔지니어의 Chat 질문 ② 이상감지 시스템이 스스로 찾아낸 이벤트.
둘 다 같은 코어로 들어간다.

"도구 8종"만 나열하면 단순 함수 호출로 읽힌다. **하위 Agent + agentic RAG + 다양한 tool calling 이
한 오케스트레이션 아래 묶여 있다**는 점을 TECH 칸에서 분명히 쓴다.

### 9-2B. 사내 공용 RAG 의 실제 사정 (사용자 확인 2026-08-08) — 문구를 정확히 쓸 것
사용자가 확인해준 바로는 이렇다. **"공용 RAG 는 아무것도 안 된다" 는 식으로 쓰면 안 된다.**

| 항목 | 사실 |
|---|---|
| 사내 공용문서 저장소·텍스트 적재 | **사내 RAG system API 로 가능하다.** 즉 텍스트 색인은 기존 자산을 쓸 수 있다 |
| 그 RAG 의 구성 | **디폴트다** — BM25 + bge-m3 임베딩 + 기본 reranker |
| 우리가 고를 수 있는 것 | **tokenizer 정도가 전부**로 보인다 |
| 따라서 못 하는 것 | 반도체 사전 등록, 사내 용어 병기(ACI→세정 후 계측), 한국어 형태소 색인, 메타 필터(eqp_id·공정·기간), 임베딩·리랭커 교체, recall 지표 열람 |

**⚠ 명명 규칙 (사용자 확인 2026-08-08) — 예시를 틀리게 쓰면 현업이 바로 알아본다**
- **설비명에는 하이픈이 없다.** `PHO-D03` 같은 표기는 존재하지 않는다 → `PHOD03` 처럼 붙여 쓴다.
- **하이픈·언더바가 붙는 것은 recipe 명이다** (예: `PH_CD_A01-3`). 분절 사고는 여기서 더 크게 난다.
- 사전 등록 대상은 설비 ID 하나가 아니다 — **EQP 정보 · STEP 정보 · recipe 명 · 계측 항목 · 불량 유형**
  까지 규칙으로 학습시켜 **어떤 것도 토큰으로 떨어지지 않게** 하는 것이 요지다.

**서술 방향** — "적재는 사내 API 로 되지만, 검색 품질을 좌우하는 손잡이가 tokenizer 하나뿐이다."
이게 "전부 막혔다" 보다 정확하고, 심사위원이 사내 RAG 를 아는 사람이어도 반박당하지 않는다.

**부수 효과(유리한 쪽)** — 텍스트 적재를 사내 RAG API 에 얹으면 중복 투자가 없다는 논거가 된다.
그 경우 자체 구축의 초점은 **이미지 검색과 도메인 특화 재순위**로 좁혀진다. 범위가 줄어 확산 비용도 준다.
다만 사용자도 "~일 수도 있다" 로 말한 미확정 사항이다. **단정해 쓰지 말고 위 표의 사실만 쓴다.**

### 9-2C. 근거 체인 — 이미지에서 원본 문서까지 (사용자 확인 2026-08-08)
**이 지원서에서 가장 강한 논거인데 아직 본문에 없다. 반드시 넣는다.**
LLM 이 지어낸 것이 하나도 섞이지 않는 5단 사슬이다.

```
① 이미지 투입      불량 이미지를 넣는다
② 유사 사고 검색   이미지 스토리지에서 임베딩 유사도로 닮은 과거 사고를 찾는다
③ 메타 키 매칭     찾은 이미지의 파일 경로·메타데이터를 키로 삼아 사고를 특정한다
④ RDB 실데이터     그 키로 사고 이력 RDB 를 조회한다.
                   이 표는 LLM 이 문서를 읽고 만든 것이 아니라 현업이 직접 기입한 원본이다
⑤ 원본 문서 매칭   RDB 의 경로로 사고 보고서 원문까지 찾아 docling·OCR 로 읽고,
                   LLM 이 그 원문을 근거로 추가 정보를 설명한다
```

**왜 이게 결정적인가 (심사에서 쓸 문장)**
- 유사도는 후보만 좁힌다. **확정은 키 조회**가 한다 — 벡터 검색의 모호함이 판정에 들어오지 않는다.
- 사고 정보의 출처가 **사람이 기입한 RDB** 다. LLM 요약본이 아니다. 감사에서 원본을 그대로 댈 수 있다.
- 문서는 경로로 매칭해 **원문을 읽는다**. 요약을 다시 요약하지 않는다.
- 결국 판단 근거가 이미지 → 키 → 원본 데이터 → 원본 문서로 **끝까지 실물에 닿아 있다.**

§0-3 주의 : 이 체인 자체는 구조 설명이라 수치가 아니다. 새 성능 수치를 붙이지 마라.

### 9-3. E2E 6단계 (Process 20점 — 도해의 뼈대)
```
입구 둘 : Chat(엔지니어 질문) / 무인(감지 이벤트 → 질문 변환, Event-to-Question Adapter)
코어 하나 : adapter → investigator ⇄ tools → judgment → action → answer → register
            증상분류    ReAct 루프로       검증기   등급표    근거    현업 확정
            규칙 로드   도구 반복 호출      5칙     + 승인    인용    → 검색 자산(선순환)
```
- 도구 8종 : SQL 5 (`get_spc_trend` `commonality_analysis` `get_master_info` `get_interlock_history`
  `search_fab_data`) · Vision 2 (`classify_wafer_map` `analyze_defect_images`) · RAG 1 (`search_inform_notes`)
- 검증기 5칙 : 스키마 / 근거 실재 / 사실 대조 / 신뢰도 규칙(High 주장 시 근거 3개 이상·반증 0) / 공백 금지
- 조치 등급 : L0 정보 · L1 알림 · **L2 현장 영향 조치 = 전건 승인 후 실행** · L3 자동 = **1차년 개방 안 함**

### 9-4. TECH 재료 (30점)
- **설계 결정 7** : ①코어 하나·입구 둘 ②조사는 ReAct 루프 ③계산은 시스템·연결은 LLM
  ④검증기 통과분만 채택 ⑤조치는 규칙표+권한별 승인 ⑥등록은 현업, 확정된 것만 검색 ⑦조사규칙은 문서로
- **차별화 4** : ①자동화가 별도 개발이 아니다(코어 공유) ②수치 환각의 발생원 제거(계산은 전부 코드)
  ③그럴듯한 오답이 채택되지 않는다(검증기 5칙) ④확산 비용이 구조적으로 낮다(조사규칙 문서만 추가)
- **성능 지표** : `recall@10 = 0.500` 실측(골든 4건 / 색인 50건). **이것 외 퍼센트 금지.**
  나머지는 지표 정의 + 회귀 게이트(변경 시마다 골든셋 러너, 미통과 시 배포 금지)로 쓴다.
